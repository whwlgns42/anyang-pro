# Dev Agent Common Rules

개발 에이전트(pm, backend, frontend, database, code-review, git-manager)의 공통 규칙이다.
에이전트가 스폰될 때 자동으로 로드되므로 따로 읽지 않는다.

이 파일이 공통 규칙의 유일한 원본이다. 같은 내용을 다른 파일에 복제하지 않는다.

## Agent Roster

| 에이전트 | 역할 |
|---|---|
| `pm` | 개발 요청의 진입점. 작업 분배와 최종 보고 취합. 코드는 쓰지 않는다 |
| `backend` | 서버, API, 비즈니스 로직. API 계약 문서의 소유자이자 frontend·database 조율 허브 |
| `frontend` | 화면과 사용자 인터페이스 |
| `database` | 스키마, 마이그레이션, 쿼리 |
| `code-review` | 코드와 문서 모순 검수. 수정 권한 없음 |
| `git-manager` | 커밋과 푸시 승인 관리 |

## Development Kickoff Order

누가 어떤 순서로 움직이는지만 정한다. 각 단계에서 지켜야 할 내용은 아래 Operating Rules에 있다.

1. pm이 요청을 파악한다. 애매한 부분이 있으면 분배하지 않고 질문을 보고한다.
2. **설계 단계**: pm이 `단계: 설계` 작업 지시서로 필요한 에이전트를 의존 순서대로 한 번에 하나씩 호출한다: database → backend → frontend (필요한 에이전트만). 뒤 에이전트는 앞 에이전트의 설계 문서를 먼저 읽는다. 각 에이전트는 설계 문서를 `status: draft`로 완성하고 보고한 뒤 끝낸다. 새 요청 때문에 이미 "승인된 설계"에 오른 문서를 고쳐야 하면, pm이 호출 전에 그 문서를 "승인된 설계"에서 빼고 사유(새 요청)를 "확인이 필요한 항목"에 적는다. 재승인은 3단계에서 받는다.
3. **사용자 승인**: pm이 새 설계 문서를 `index.md`에 등록하고, 문서 커밋을 git-manager에게 맡긴 뒤 설계 문서 목록을 보고한다. 메인 세션이 사용자 승인을 받는다. 설계 승인은 그 문서에 적힌 값의 확정이다. 사용자가 확정하지 않겠다고 한 값이 있으면 pm은 그 문서의 승인을 기록하지 않고 "확인이 필요한 항목"에 올린다. 사용자가 반려하거나 수정을 요청하면 메인 세션이 그 내용으로 pm을 다시 호출하고, pm은 반려 내용을 프로젝트 문서에 기록한 뒤 수정이 필요한 설계만 2단계로 다시 맡긴다.
4. **구현 단계**: pm이 먼저 프로젝트 문서의 "승인된 설계" 절에 승인 내용을 `- [[문서명]] — 승인일 YYYY-MM-DD, 승인자 user` 형식으로 기록한다. 그다음 승인된 설계만 `단계: 구현` 작업 지시서로 다시 분배한다. 의존이 있으면 database → backend → frontend 순서로 호출하고, 의존이 없고 수정할 파일이 겹치지 않을 때만 병렬로 호출한다. 각 에이전트는 그 기록을 확인하고, 설계 문서와 dev-task 문서를 `status: active`로 바꾸면서 승인으로 확정된 값의 `(미확정)` 표시를 지운 뒤 구현한다. 구현·검수 중에는 누구도 승인된 설계 문서의 내용을 고치지 않는다(`status` 줄과 `(미확정)` 표시만 바꿀 수 있다). 설계를 바꿔야 하면 "설계 변경 필요"로 보고한다. 그러면 pm이 그 문서를 "승인된 설계"에서 빼고 사유를 "확인이 필요한 항목"에 적은 뒤 3단계로 재승인을 받는다. 테스트를 통과하면 기능 단위마다 git-manager가 커밋한다.
5. code-review가 코드와 문서를 검수한다.
6. pm이 새 문서를 `index.md`에 등록하고, 코드 커밋에 포함되지 않은 문서의 커밋을 git-manager에게 맡긴 뒤 결과를 취합해 보고한다.

설계 단계와 구현 단계는 서로 다른 호출이다. 서브에이전트는 세션 도중에 상위 세션으로 돌아가지
못하므로, 승인 게이트는 호출을 나눠서만 만들 수 있다.

## Operating Rules

1. 애매한 내용은 임의로 만들거나 고치거나 지우지 않는다. 확실해질 때까지 사용자에게 되묻는다. 서브에이전트(pm 포함)는 사용자에게 직접 묻지 못하므로, 작업을 멈추고 보고의 "미해결 질문"에 적은 뒤 끝낸다. 되돌릴 수 없는 작업의 승인도 같은 방법으로 받는다.
2. 개발은 설계 → 문서화 완료 → 구현 순서를 지킨다. 문서가 끝나기 전에 코드를 쓰지 않는다. 설계 문서에는 테스트 방법도 적는다.
3. 파일 삭제는 사용자 승인을 받은 뒤에만 한다.
4. 기능, 페이지, 이벤트 단위로 작업이 끝나면 테스트·빌드를 실행하고, 통과한 것만 바꾼 파일 목록과 함께 git-manager에게 커밋을 위임한다. 실패하면 커밋하지 않고 보고한다. 코드 없이 문서만 바뀐 경우(설계 문서, `index.md`·`log.md`, 프로젝트 문서, errors 문서)는 테스트 없이, 단계가 끝날 때 pm이 파일 목록을 모아 git-manager에게 커밋을 위임한다. 저장소를 바꾸는 git 명령은 git-manager만 실행한다. 원격 대비 로컬 커밋이 5개 이상 쌓이면 push 여부를 사용자에게 확인받는다. 승인 없는 push는 금지한다. 저장소가 없을 때의 `git init`도 사용자 승인 대상이다.
5. 폴더명과 파일명은 영문 소문자 명사로, 단어는 하이픈으로 잇는다.
6. 작업이 중간에 멈추면 다음 세션이 이어받을 수 있도록 `AI-Sessions/conversations/`에 인수인계를 남긴다.
7. 오류가 나면 `AI-Sessions/wiki/errors/`에 기록해 같은 실수를 반복하지 않게 한다.
8. 모르거나 확인되지 않은 것은 "모른다", "불가능하다"라고 분명히 답한다. 추측으로 채운 내용을 산출물에 넣지 않는다.
9. 로그인 자격 증명, 접속 정보, 개인정보는 문서에 남기지 않는다. 코드에도 하드코딩하지 않고 환경변수로 받으며, `.env` 같은 파일은 커밋하지 않는다.
10. 작업이 끝나면 호출한 쪽(보통 pm)에게 보고하고 세션을 끝낸다. 보고에는 파일 경로와 요약만 담고 문서 본문을 붙이지 않는다. 새로 만든 wiki 문서 경로와 커밋 해시를 빠뜨리지 않는다. 지시받지 않은 작업을 임의로 덧붙이지 않는다. 개발 에이전트는 `.claude/rules/knowledge-ops.md`의 Completion Rule보다 이 보고 형식을 우선한다.
11. 에이전트가 제안한 값과 사용자가 확정한 값을 구분한다. 제안을 근거로 다른 문서를 고치지 않는다. 확정 여부가 불확실하면 원본 문서에 그 값이 실제로 기록되어 있는지 확인한다. 기록이 없으면 아직 미확정이다. 표기법은 `.claude/rules/knowledge-ops.md`의 "확정 값과 제안 값"을 따른다.
12. 확인이 필요한 사항은 즉석 질문으로 끝내지 않고 해당 프로젝트 문서의 "확인이 필요한 항목" 절에 기록한다. 세션이 끊겨도 무엇을 물어야 하는지 남기기 위함이다. 프로젝트 문서의 소유자는 pm이므로 기록은 pm이 한다. 다른 에이전트는 보고의 "미해결 질문"에 적는다.

## Enforcement

아래 규칙은 글이 아니라 `.claude/settings.json`의 훅(`scripts/agent_guard.py`)과 권한 설정이 강제한다.
막히면 우회하지 말고 이유를 보고한다.

- 에이전트 호출: 각 에이전트 정의의 `tools`에 적힌 `Agent(...)` 목록 밖은 거부된다.
- git: 저장소를 바꾸는 명령은 git-manager만 실행할 수 있다(`git -C <dir> ...` 형태 포함).
- 설계 잠금: 프로젝트 문서의 "승인된 설계" 절에 오른 design 문서는 `status` 줄과 `(미확정)` 표시 말고는 Write·Edit가 거부된다.
- `log.md`: 형식과 시간순이 어긋나면 린트 FAIL이다.
- `git push`, `git -C ...`, `git init`, `git reset --hard`, `rm -rf`는 누가 실행하든 사용자 확인 창이 뜬다.
- 끝낼 때 자기 소유 문서(또는 소유자가 없는 문서)에 린트 FAIL이 있으면 한 번 되돌려진다. `index.md` 미등록은 다른 에이전트에게서는 제외되고, pm에게는 모든 문서에 대해 검사된다.

## Document Consistency Rules

문서가 많아져도 서로 어긋나지 않게 하는 장치다. 문서를 쓰는 모든 에이전트에 적용된다.

- **소유권**: wiki 문서 frontmatter에 `owner: <에이전트명>`을 넣는다. 소유자가 아닌 에이전트는 그 문서를 고치지 않는다. 수정이 필요하면 소유 에이전트를 호출하거나 pm에게 넘긴다.
- **중복 금지**: 새 문서를 만들기 전에 `index.md`와 해당 wiki 폴더를 먼저 검색한다. 같은 주제의 문서가 이미 있으면 새로 만들지 말고 그 문서를 갱신한다.
- **용어 고정**: 용어는 `AI-Sessions/wiki/concepts/glossary.md`를 따른다. 새 용어는 glossary에 추가한 뒤 쓴다. 추가는 누구나 할 수 있지만, 이미 있는 정의를 바꾸거나 지우려면 pm에게 보고해 승인을 받는다.
- **동시 수정 금지**: 여러 에이전트가 같은 파일을 동시에 고치지 않는다. pm은 병렬로 호출할 때 각자 건드릴 파일이 겹치지 않게 나눈다.
- **링크와 등록**: 양방향 링크, `index.md` 등록, 결정 교체(`status: superseded`) 규칙은 `.claude/rules/knowledge-ops.md`의 Link Rules를 따른다. 여기에 다시 적지 않는다.
- **검증**: 문서 작업이 끝나면 `bash scripts/lint-wiki.sh`를 실행한다. `FAIL`은 고치고, `WARN`은 판단해 넘어간다. 링크 규칙과 판정 기준은 `.claude/rules/knowledge-ops.md`에 있다.

## Document Format

`.claude/rules/knowledge-ops.md`의 Document Format을 따른다. 여기에 다시 적지 않는다.
두 곳에 적으면 한쪽만 고쳐져서 어긋난다. 개발 에이전트가 만드는 설계·태스크 문서에도
같은 형식이 적용된다.

## Peer Communication

호출할 수 있는 상대는 각 에이전트 정의의 `tools`에 적힌 `Agent(...)` 목록이다. 구조는 의존
관계를 따른다. frontend와 database는 서로 직접 조율하지 않고 backend를 거친다. API 계약을
backend 문서 한 곳에 모으기 위해서다. git-manager는 호출을 받기만 한다.

서브에이전트는 메인 대화 아래 3단계까지만 뜬다 (메인 → pm → backend → frontend). 그래서
pm이 아닌 동료 에이전트의 호출로 떠 있을 때는 조율 답변과 자기 소유 문서 기록만 하고,
구현·커밋·추가 호출은 하지 않는다. 구현은 pm의 분배로만 시작한다. 동료를 부를 때는 프롬프트
첫 줄에 누가 부르는지와 단계(`설계` / `구현` / `검수`)를 밝힌다.

설계 단계가 아닐 때(구현·검수 중) 동료의 호출로 떴다면 자기 소유 문서도 고치지 않고 답변만 한다.
pm이 병렬로 분배한 같은 역할 에이전트가 그 문서를 동시에 고치고 있을 수 있기 때문이다. 설계
문서에 없는 것을 새로 정해야 한다면 그것은 설계 변경이다. "설계 변경 필요"라고 돌려주고, 호출한
쪽은 작업을 멈추고 pm에게 미해결 질문으로 보고한다. 이후 처리는 Kickoff 4를 따른다.

호출 한 번마다 새 세션이 뜨고 규칙 파일 전체를 다시 읽는다. 그래서 다음을 지킨다.

- 호출하기 전에 상대가 소유한 design 문서를 먼저 읽는다. 답이 문서에 있으면 호출하지 않는다.
- 질문은 한 번의 호출에 모아서 보낸다.
- 설계 단계라면 호출받은 쪽은 합의 내용을 자기 소유 문서에 쓰고, 문서 경로와 한 줄 요약만 돌려준다.
  호출한 쪽은 값을 옮겨 적지 않고 그 문서를 링크한다.
- 같은 주제로 3회를 넘겨 왕복하지 않는다. 합의되지 않으면 pm에게 넘겨 사용자 확인을 받는다.
- 대화로 정한 내용은 반드시 문서로 남긴다. 호출한 세션은 끝나면 사라지고 파일만 남는다.

## Jev 도입 제안

Jev(TypeSafe System One 모델)는 좁은 판단 하나를 빠르게 확률로 돌려준다. 개발 중 아래 조건을
모두 만족하는 판단을 만나면 보고에 "Jev 도입 제안"을 적는다. 해당이 없으면 이 항목을 쓰지 않는다.

- 조건: (1) 결과가 좁은 판단이다 — 예/아니오(Noul), 정해진 목록에서 하나(Choice), 정도(Score).
  (2) 요청마다, 항목마다 반복된다. (3) 지금 LLM 호출이 그 판단을 하거나 설계상 하려 한다.
- 제외: 조건문·정규식으로 결정적으로 풀리는 판단(코드로 처리한다), 강제 장치인 훅 차단·린트
  FAIL·권한 규칙(확률 판정을 넣지 않는다), 문서·코드·리뷰 본문 생성.
- 하네스 자체의 문서 판단(관련 문서 찾기, 중복 확인, Save Filter)에는 이미 Jev를 쓴다. 절차는
  `.claude/rules/knowledge-ops.md`의 "Jev 보조 판단"에 있다. 이 절은 제품 코드에 대한 제안만 다룬다.
- Jev 호출은 backend를 거친다. 클라이언트 코드에 API 키를 두지 않는다.
- 수치: 현재 비용은 설계 문서나 코드에서 호출 수 × 입력·출력 토큰 × 빈도로 센다. Jev 비용은
  `TYPESAFE_API_KEY`가 있으면 대표 입력으로 1회 호출해 응답 시간과 응답의 토큰 사용량을 잰다
  (`typesafe-ai` 스킬 참고). 키가 없으면 "측정 불가"로 쓴다. 모든 수치에 `(추정, 근거: …)`를
  붙이고, 근거 없는 수치는 쓰지 않는다. 측정 입력에 `AI-Sessions/raw/` 원문과 개인정보를 넣지 않는다.
- 형식:
  ```text
  - 위치: <파일/기능/설계 문서 링크>
  - 판단: <Noul|Choice|Score> — <무엇을 판정>
  - 속도: 현재 <값> → Jev <값> (추정, 근거: …)
  - 토큰: 현재 <값>/회 × <빈도> → Jev <값> (추정, 근거: …)
  - 주의: 오판 시 영향, 외부로 보내는 데이터 범위
  ```
- 흐름: pm이 프로젝트 문서의 `## Jev 도입 제안` 절에 옮겨 적고 최종 보고에 담는다. 제안은
  제안일 뿐이다. 도입은 설계 변경이므로 Kickoff 2~3단계의 승인을 거친다.

## Skill Usage

스킬 규칙은 여기 한 곳에만 둔다. 각 에이전트 파일에 따로 적지 않는다.

- 스킬은 프로젝트 `.claude/skills/`에 설치된 것만 쓴다. 전역 스킬은 쓰지 않는다.
  스킬·플러그인 대장과 역할별 권장 스킬은 `.claude/skills/README.md`에 있다 — 각 항목의
  설치 상태, 설치 명령, 출처 URL을 담는다.
- 스킬이 필요하면 먼저 대장에서 해당 항목을 찾는다.
  - `상태: 설치됨` → 바로 호출해서 쓴다.
  - `상태: 미설치` + 설치 명령 있음 → 그 명령을 사용자에게 그대로 안내한다.
    에이전트는 `/plugin` 등 슬래시 명령을 직접 실행하지 못하므로 사용자가 실행해야 한다.
  - `출처: 확인 필요` → 사용자에게 URL을 묻는다. 추측한 URL을 안내하지 않는다.
  설치된 뒤 반드시 그 스킬로 작업한다. 우회해서 임의로 진행하지 않는다.
- 스킬을 새로 설치하거나 제거하면 `.claude/skills/README.md`의 대장을 즉시 갱신한다.
- 스킬이 아닌 개발 도구(`gh` CLI 등)가 없어서 막히면 `.claude/rules/dev-environment.md`의
  도구 대장에서 설치 명령을 찾아 사용자에게 안내한다.
- 쓸 만한 스킬이 무엇인지 모르겠으면 추측하지 말고 사용자에게 묻는다.
  스킬 이름이 정확한지 불확실할 때도 마찬가지다.
