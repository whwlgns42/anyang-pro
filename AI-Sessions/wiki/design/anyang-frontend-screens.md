# 안양 청년정책 비서 — Frontend 화면 설계

## Summary

Next.js(App Router) PWA, 모바일 우선. 로그인/가입 → 온보딩(프로필) → 채팅/추천 공지 피드를
중심으로, 알림 설정·"AI가 기억하는 내 정보"·대화 히스토리 목록 화면을 둔다(모두
[[anyang-service-scope]]로 채택 확정). API는 모두 [[anyang-backend-api]]를 근거로 삼는다.
화면 포함 여부는 확정됐고, 세부 구조·문구·레이아웃 값도 사용자 설계 승인으로 확정됐다.
비밀번호 재설정 화면은 1차 출시에서 제외로 **확정**됐다
([[anyang-service-scope]], user, 2026-09-27) — 별도 화면을 만들지 않고, 로그인 화면에
"비밀번호를 잊었다면 Google로 로그인" 안내로 대체한다(1절). `/admin` 관리자 화면 4종(공지
수집 관리·알림 발송 현황·사용자 관리·통계·외부 API 사용량)도 채택 확정
([[anyang-service-scope]], user, 2026-09-27)이며, 세부는 이 문서의 10~13절에서 다룬다.
계정 탈퇴 화면(`/settings/account`, 8-1절)도 이번 반영으로 추가됐다.

**2026-09-28 개정(확인 항목 22·23)**: 채팅 인용 카드(3절)를 backend
[[anyang-backend-api#3-2. 채팅 인용 공지 스트림 계약 (신규, 제안, 미확정 — 확인 항목 22 반영)]]의
`event: citations` 계약에 맞춰 표시 필드·위치·빈 목록 처리를 구체화했고, 관리자 공지 수집
관리(11절)에 `GET /api/admin/notices`([[anyang-backend-api#13-1. 공지 수집 관리]]) 기반 "공지
목록" 탭을 추가했다. 둘 다 값은 확정됐다.

**2026-09-28 추가 개정(확인 항목 29)**: 비밀번호 최소 8자, 로그인 실패·가입 시도 15분 5회
초과 시 일시 차단이 확정됐다(user, 2026-09-28,
[[anyang-backend-api#1-6. 로그인 실패·가입 시도 제한 (신규, 확인 항목 29)]]). 1절 로그인/가입
화면에 비밀번호 길이 힌트·차단 메시지 표시 방식을 추가했다(1-1절, 문구·배치는 frontend
제안대로 확정됐다).

**2026-09-28 3차 개정(확인 항목 41)**: 사용자 결정으로 동의 화면(7절)·처리방침(9절)의
서술에서 국가명(중국·국외·미국 등)·서비스명(DeepSeek·Gemini)·상세 고지(무료 티어, 임베딩,
RAG 등)를 뺀다. 체크박스 코드 식별자 `overseas_transfer`, 필수 검증, API 호출 형식은
그대로 둔다. 새 문구는 frontend 제안(미확정) — 재승인으로 확정. 기존 동의 기록은 유지하고
재동의를 요구하지 않으므로 `POLICY_VERSION`은 올리지 않는다(18번 재동의 강제 원칙의 예외,
신규 가입자에게만 새 문구가 보인다). 법적 근거(국외 이전 사실이 동의·처리방침 어디에도
남지 않는 위험)는 사용자가 별도로 인지했다([[anyang-youth-policy-assistant]] 확인 항목
41 (b)) — 이 설계 문서는 그 위험 판단을 다루지 않는다.

**2026-09-29 4차 개정(확인 항목 43, draft)**: 사용자가 대화에서 직접 말한 이름·호칭을
AI가 기억해 다음 대화에도 활용하도록 결정했다(user, [[anyang-ai-models-data-transfer]]).
frontend 영향은 두 가지다.
- 6절 "AI가 기억하는 내 정보" 화면 자체(목록 조회·수정·삭제 구조, 빈 목록 문구)는
  **변경 없음** — [[anyang-database-schema#user_preferences — 대화에서 추출한 선호, 벡터.
  "AI가 기억하는 내 정보" 화면의 데이터]]의 "채팅 기억 자동 추출 시 중복 방지·갱신" 절이
  같은 사실을 갱신(UPDATE)하고 새 사실일 때만 추가(INSERT)하는 정책이라, 추출 빈도가
  매 답변으로 늘어도 사용자당 행 수는 느리게 늘어난다(database 문서 실측 근거). `GET
  /api/preferences`도 상한·페이지네이션 없이 전체 목록을 반환하는 설계 그대로 두어도
  화면이 감당한다. 그래서 페이지네이션을 추가하지 않는다.
- 다만 이름까지 기억되는 사실을 사용자가 알기 어려워 6절에 안내 문구를 추가하고(아래),
  9절 처리방침에 없던 "이름 등을 기억해 활용한다"는 고지를 새로 넣는다. 두 문구 모두
  frontend 제안(미확정) — 설계 재승인으로 확정.

**2026-10-04 5차 개정(확인 항목 55, draft)**: 공지 화면에 사용자 시안(별표 고정 공지, "이미지" 배지, 첨부 파일명, 원문 페이지 링크)을 반영하고 목록을 탭 복귀·재진입 때 다시 불러온다 ([[anyang-service-scope]] "공지 화면 표시" 행, user, 2026-10-04). 바뀐 곳은 "청안 디자인 적용 화면 스펙"의 공지 목록·공지 상세 절과 4절 응답 필드 줄뿐이고 하단 탭바·다른 화면은 그대로다. 확정은 별표·배지 둘 다, 첨부는 링크 정보만, Realtime 없음, 탭 복귀·재진입 재조회까지다. 시각 세부(별표, 칩 모양, 재조회 간격 등)와 정렬·`image_count` 정의도 2026-10-04 사용자가 제안대로 확정했다. 미확인은 55-i(첨부 직접 링크) 하나다.

**2026-10-04 6차 개정(확인 항목 56, draft)**: 안양시가 클라우드 IP를 막아 공지 수집을 UNO Q 보드가 맡는다([[anyang-board-collector]]). 바뀌는 화면은 관리자 `/admin/collect-runs`의 "실행 이력" 탭 하나뿐이다(11절 "56 개정"). 사용자 화면(`/notices`, `/notices/[id]`, 채팅 인용)은 변경 없음 — 이번 수집 주체 변경은 DB·API 응답 형식을 바꾸지 않는다([[anyang-board-collector]] Summary). 이 개정의 모든 값은 frontend 제안이라 `(미확정)`이고 설계 재승인으로 확정된다. 새 API는 필요 없다(11절).

**2026-10-04 8차 개정(확인 항목 60, draft)**: 채팅에서 인용 공지로 갔다가 뒤로 오면 대화·인용 카드·스크롤이 유지되도록 3-1절을 더한다(같은 탭 sessionStorage 보관, URL에 `conversation_id` 반영, 로그아웃 정리). 사용자 결정 ①·②(프로젝트 문서 확인 항목 60)에서 직접 나오지 않는 값은 모두 `(미확정)`이다. backend·DB 변경 없음.

**2026-10-04 7차 개정(확인 항목 58, draft)**: 알림 설정 화면에 "테스트 알림 보내기" 버튼을 더한다(청안 알림 절 "테스트 알림 보내기", 서비스워커 절 `url` 처리). 사용자가 승인한 범위(재승인 없음)는 버튼, 결과 안내 3가지(성공 n대 / 구독 없음 / 잠시 후 다시 시도), 기존 화면 스타일, 테스트 payload에서도 되는 알림 클릭 이동뿐이다. 버튼 위치·표시 조건·문구·그 밖 상태(403·네트워크 오류·실패만 있는 200 등)는 frontend 제안이라 `(미확정)`이다. API 계약은 [[anyang-backend-api#8-1. 테스트 알림 (신규, 2026-10-04, 확인 항목 58)]]이고 옮겨 적지 않는다.

**2026-10-03 청안 디자인 개정(확인 항목 52)**: 팀원 디자인 소스 청안(cheongan)을 웹(PWA)에
반응형(모바일 390 / 태블릿 768 / 데스크톱 1200, 데스크톱은 사이드바)으로 적용한다
([[anyang-cheongan-design-adoption]]). 이 개정의 모든 값은 사용자 확정된 3가지(웹만, 토큰 파일
그대로 사용, 반응형 3폭) 외에는 `(미확정)`이다. 바뀌는 것은 (1) 공통 레이아웃의 하단 탭 3개 → 4개와
데스크톱 사이드바, (2) 채팅·공지 목록·공지 상세·알림 설정·"AI가 기억하는 내 정보"의 화면 구성과
외형, (3) 새 내 정보 화면(`/settings`)이다. **API 호출·응답·가드·문구 테스트 대상 고정 문구 등 동작은
바뀌지 않는다.** 새 스펙은 아래 "청안 디자인 적용 화면 스펙" 절에 모았고, 이 문서의 다른 절에서
화면 구성·레이아웃을 말하는 부분이 그 절과 다르면 그 절이 우선한다(충돌하는 줄은 직접 고쳤다).

두지 않는다. 관리자 화면은 `/admin`을 공통 레이아웃(11~14절 하위 탭)으로 두고
`/admin/collect-runs`, `/admin/notify-logs`, `/admin/users`, `/admin/api-usage`로
나눈다(제안).

### 공통 레이아웃 (모바일 우선)

- 뷰포트 기준 390px(청안 시안) 우선 설계, 태블릿 768·데스크톱 1200 이상은 아래 "청안 디자인 적용 화면 스펙"의 "공통 틀"을 따른다(2026-10-03 개정: 이전의 "중앙 정렬 고정폭 480px, 데스크톱 전용 레이아웃 없음"을 대체).
- 내비게이션: 모바일·태블릿은 하단 탭 4개(대화 / 공지 / 알림 / 내 정보), 데스크톱은 사이드바 — 구성은 "공통 틀"에 있다(2026-10-03 개정: 이전의 "채팅 / 공지 피드 / 설정" 3개를 대체). 로그인 전 화면(로그인·가입·온보딩)과
  개인정보 동의 화면에는 탭을 두지 않는다.
- 공통 인증 가드: 로그인하지 않은 사용자가 `/chat`, `/notices`, `/settings/*`에 접근하면
  `/login`으로 리다이렉트(제안 — Auth.js 세션 확인 기준, [[anyang-backend-api#1. 인증 (Auth.js v5)]]).
- 온보딩 미완료(프로필 없음) 사용자가 `/chat` 등에 접근하면 `/onboarding`으로 리다이렉트
  (제안 — `GET /api/profile` 404/빈 값 기준).
- **403 응답 분기 (분기 자체는 backend
  [[anyang-backend-api#1-4. 403 응답 에러 코드 (제안)]]의 에러 코드 존재를 전제)**:
  인증 필요 API가 403을 반환하면 공통 인증 가드가 응답 body의 `error` 코드로 아래처럼
  분기한다.
  - `ACCOUNT_SUSPENDED` (backend [[anyang-backend-api#1-2. 정지 계정 제한 방식]]) →
    정지는 로그인 자체를 막지 않는다. 로그인은 항상 허용되고, 로그인 성공 시 세션에 담기는
    `session.suspended`(boolean, backend 제안) 플래그가 true면 로그인 직후 정지 안내
    화면(1절)으로 보낸다(세션은 유지, 로그아웃하지 않는다). 정지 안내 화면에서 가능한 동작은
    로그아웃과 탈퇴(8-1절, `DELETE /api/account`)뿐이고, 그 외 화면·API 접근은 서버가 매
    요청 403 + `ACCOUNT_SUSPENDED`로 거부하므로, 공통 인증 가드가 이 응답을 받으면 현재
    화면 대신 정지 안내 화면으로 다시 보낸다(세션 종료 없음, 제안).
  - `CONSENT_REQUIRED` (재동의 강제, **확정 원칙**, [[anyang-service-scope]], user,
    2026-09-27) → 현재 화면 대신 `/consent`로 리다이렉트한다. `/consent` 화면에서 두
    체크박스를 다시 체크해 `POST /api/auth/consent`를 재호출하면 원래 가려던 화면(또는
    `/chat` — 복귀 경로 저장 여부는 YAGNI로 우선 `/chat` 고정 제안)으로 이동한다.
    `/consent` 화면에도 탈퇴 경로(8-1절)를 함께 제공한다 — `DELETE /api/account`는 재동의
    필요 상태에서도 호출 가능하다(backend 1절 예외).
  - `ADMIN_ONLY` → `/admin/*` 전용(아래 "관리자 가드" 참고), 관리자가 아니라는 안내 후
    `/chat`으로 보낸다.
  - `ADMIN_EMAIL_RESERVED`는 이 공통 가드가 아니라 1절 가입 화면에서만 인라인 오류로
    처리한다(가입 시도 응답이라 리다이렉트 대상이 없음).
- **관리자 가드 (확정 원칙, [[anyang-service-scope]], user, 2026-09-27)**: 관리자 판정은
  서버만 한다. `ADMIN_EMAILS` 목록은 서버 환경변수([[anyang-backend-api#13-0. 공통 인가]])
  로만 존재하며, 클라이언트 코드·번들·정적 자산 어디에도 이메일 목록을 넣지 않는다(임포트,
  `NEXT_PUBLIC_` 환경변수, 빌드 타임 상수 모두 금지). 관리자 판정은 **이번 세션의 로그인을
  Google로 한 경우에만** 통과한다(backend 13-0절 — JWT의 `provider` 클레임 기준, 계정
  자체가 아니라 "지금 이 요청이 어떻게 인증됐는가"로 판정) — 같은 이메일이 과거 Google로
  가입했더라도 이번 세션을 이메일·비밀번호(Credentials)로 로그인했다면 `ADMIN_EMAILS`에
  있어도 관리자가 될 수 없다. `/admin/*` 화면은 진입 시 13-0절
  대상 아무 관리자 API나 1회 호출해 401이면 `/login`으로, 403(`ADMIN_ONLY`)이면 "관리자
  계정이 아닙니다" 안내와 함께 `/chat`으로 리다이렉트하고, 200이면 화면을 그린다(제안
  — 클라이언트 쪽 "관리자인지" 캐시나 별도 `/api/admin/me` 없이 실제 데이터 API
  응답 코드로만 판단, YAGNI). 화면 자체의 존재나 링크는 숨기지 않아도 되지만(13-0절 403
  채택 원칙과 동일), 데이터는 서버 응답 없이는 절대 렌더링하지 않는다.

### 1. 로그인/가입 화면 (`/login`)

- 구성 요소: "Google로 계속하기" 버튼(OAuth 리다이렉트), 이메일·비밀번호 입력 폼(로그인),
  "계정이 없다면 가입" 전환 링크 → 같은 화면에서 폼 모드만 전환(가입 시 비밀번호 확인 입력 추가). 비밀번호 입력 아래에 "비밀번호를 잊었다면 Google로 로그인" 안내 문구(제안
  문구)를 둔다 — 별도 비밀번호 재설정 화면·링크는 만들지 않는다(1차 출시 제외 확정,
  [[anyang-backend-api#1-1. 이메일 인증·비밀번호 재설정 — verification_tokens 미사용에 따른 정리 (확정)]]).
  Credentials 가입 계정은 비밀번호를 잊으면 이 서비스 안에서 복구 수단이 없다는 한계가 있다
  (backend 1-1절).
- 가입 흐름: 이메일·비밀번호 입력 → 동의 체크박스(`/consent` 화면, 7절 참고)를 거쳐
  체크된 상태로 `POST /api/auth/register`(body 형식은 backend
  [[anyang-backend-api#1. 인증 (Auth.js v5)]]의 `{ email, password, consents: {
  collection_use, overseas_transfer } }`를 그대로 따른다 — 값은 여기서 복제하지 않는다) 호출
  → 성공 시 자동 로그인 후 `/onboarding`으로 이동. 두 체크박스가 모두 체크되지 않으면 제출
  버튼 비활성(제안). 이메일 중복(409) 시 인라인 오류 메시지. 403 +
  `{ error: "ADMIN_EMAIL_RESERVED" }`([[anyang-backend-api#1-4. 403 응답 에러 코드 (제안)]],
  관리자 이메일로 비밀번호 가입을 시도한 경우) 시에도 인라인 오류로 "이 이메일은 비밀번호로
  가입할 수 없습니다. Google로 로그인해 주세요"(제안 문구)를 표시한다.
- 로그인 흐름: Auth.js Credentials 로그인 → 성공 시 프로필 존재 여부에 따라 `/chat`
  또는 `/onboarding`. 401 시 "이메일 또는 비밀번호가 올바르지 않습니다"(제안 문구).
- **정지된 계정 로그인**(제안 문구 — [[anyang-backend-api#1-2. 정지 계정 제한 방식]]
  기준, 에러 코드는 [[anyang-backend-api#1-4. 403 응답 에러 코드 (제안)]]의
  `ACCOUNT_SUSPENDED`): **로그인 자체는 정지 여부와 무관하게 허용된다**(이전 "로그인 시점
  차단" 제안은 폐기). 이메일·비밀번호, Google 로그인 모두 정상적으로 성공하고, 세션에 담긴
  `session.suspended`가 true면 로그인 직후 정지 안내 화면(공통 레이아웃 절 참고)으로
  이동시켜 "이용이 정지된 계정입니다"(제안 문구)를 보여준다. 정지 안내 화면에서 가능한
  동작은 로그아웃과 탈퇴(`/settings/account`, 8-1절)뿐이며, 그 외 화면 이동이나 API 호출은
  서버가 매 요청 403 + `ACCOUNT_SUSPENDED`로 거부하므로 공통 인증 가드가 이를 감지해 정지
  안내 화면으로 돌려보낸다(세션은 종료하지 않는다, 제안). 정지 안내 화면에는 항상
  탈퇴 경로(8-1절) 링크를 함께 제공한다 — `DELETE /api/account`는 정지 상태에서도 호출
  가능하다(backend 1-2절 예외).
- Google 로그인 흐름: Auth.js `signIn('google')` → 콜백 후 신규 사용자는 동의 여부를
  판별해(제안 — `GET /api/profile` 401 아닌 403 등 동의 필요 신호 기준, backend 1절 참고)
  미동의 상태면 `/consent`로 보내 체크박스 동의 후 `POST /api/auth/consent`(body는 이메일
  가입과 같은 `{ consents: { collection_use, overseas_transfer } }`, backend 1절) 호출 →
  성공 시 `/onboarding`. 이미 동의한 기존 사용자는 프로필 존재 여부로 `/chat` 또는
  `/onboarding`.
- **`OAuthAccountNotLinked` 오류**(제안 문구 — [[anyang-backend-api#1-5. 이메일 계정 연결 정책 (신규, 제안)]]
  기준): 같은 이메일로 이미 이메일·비밀번호 계정이 있으면 Google 로그인이 Auth.js
  `OAuthAccountNotLinked` 에러로 실패한다(계정 자동 연결을 켜지 않는 것이 채택된 기본값이라
  발생하는 정상 동작). 이 오류를 비밀번호 오류와 구분해 안내한다: "이 이메일은 이미
  비밀번호로 가입되어 있습니다. 비밀번호로 로그인하거나, 본인 계정이 아니면 관리자에게
  문의해 주세요"(backend 1-5절 문구 그대로).
- 비밀번호 재설정: 1차 출시 제외로 **확정**됐다([[anyang-service-scope]], user, 2026-09-27).
  이 화면·엔드포인트·이메일 발송 수단을 만들지 않는다(위 구성 요소 항목의 안내 문구로 대체).

### 1-1. 비밀번호 길이·시도 제한 안내 (신규, 확인 항목 29)

비밀번호 최소 8자, 로그인 실패·가입 시도는 15분에 5회 초과 시 일시 차단은 **확정**됐다(user,
2026-09-28, [[anyang-backend-api#1-6. 로그인 실패·가입 시도 제한 (신규, 확인 항목 29)]]). 아래
문구·배치는 frontend 제안이다.

- **가입 폼 비밀번호 힌트(제안)**: 비밀번호 입력 필드 아래 "비밀번호는 8자 이상이어야
  합니다" 힌트 텍스트를 상시 노출한다(제안 — 포커스 시에만 보일지는 별도 확인 없이, 1차
  제안은 상시 노출). 제출 전 클라이언트에서도 길이 8자 미만이면 인라인 오류로 표시하고 제출을
  막는다(제안) — 서버 400 `{ error: "PASSWORD_TOO_SHORT" }`(backend 1-6절) 응답을
  받으면 클라이언트 검증을 우회한 경우를 대비해 같은 자리에 같은 문구를 표시한다.
- **로그인·가입 차단 메시지(제안)**: 로그인·가입 모두 429 +
  `{ error: "TOO_MANY_ATTEMPTS" }`(backend 1-6절) 응답을 받으면 폼 상단 또는 제출 버튼
  근처에 "잠시 후 다시 시도해 주세요" 계열 인라인 오류 메시지를 표시한다(문구 예시, 제안). 로그인 401(비밀번호 오류) 메시지와 시각적으로 구분한다(제안 — 구체적
  스타일은 25번 결정의 taste-skill 적용 범위 안에서 정한다).
- 두 메시지 모두 계정 존재 여부를 유추할 수 있는 문구(예: "이 이메일은 존재하지 않습니다")는
  쓰지 않는다(제안 — backend 1-6절 "계정 열거 방지" 원칙과 일관).

### 2. 온보딩 — 프로필 입력 (`/onboarding`)

- 항목: 4개로 **확정**([[anyang-service-scope]], user, 2026-09-27) — `birth_year`, `gender`,
  `occupation_type`, `enrollment_status`([[anyang-database-schema#profiles (항목 범위·코드값
  셋·컬럼 타입 모두 확정)]]). 더 늘어나지 않는다.
- 입력 컴포넌트(제안): `birth_year` — 네이티브 `<select>` 또는 `<input type="number">`
  (연도 범위, YAGNI — 커스텀 날짜 피커 불필요). `gender`, `enrollment_status` — 라디오 버튼
  그룹. 표시 문구는 [[anyang-service-scope]] "프로필 선택지" 행의 한국어 표시명을 그대로 쓴다.
  `occupation_type`은 선택지가 8개로 다른 두 항목보다 많아 라디오 그룹 대신 네이티브
  `<select>`를 쓰는 제안(여덟 개 라디오 버튼이 모바일 화면에서 세로로 길어지는 것을
  피하기 위함, 설계 승인으로 확정). 표시 문구는 마찬가지로 [[anyang-service-scope]]의 한국어
  표시명을 쓴다.
- 제출: `PUT /api/profile`([[anyang-backend-api#2. 프로필 CRUD]]) → 성공 시 `/chat` 이동.
- 모든 항목 null 허용(database 설계 원칙)이므로 "나중에 입력" 건너뛰기 버튼 포함(제안,
  건너뛰면 빈 값으로 `PUT` 호출).

### 3. 채팅 화면 (`/chat`)

> 2026-10-03 청안 개정: 화면 구성·외형은 "청안 디자인 적용 화면 스펙"의 채팅 절이 우선한다. 스트림 파싱·인용 계약·링크 동작은 아래 그대로다.

- 구성: 메시지 리스트(사용자/AI 말풍선), 하단 입력창, 전송 버튼, 대화 히스토리 목록 진입점
  (`/conversations`, 8절)으로 가는 버튼/아이콘(제안 — 위치는 상단 헤더).
- 스트리밍: `POST /api/chat`([[anyang-backend-api#3. 채팅 — DeepSeek 스트리밍 + RAG]])의
  SSE 응답을 파싱한다(제안 — 파서 분기는 backend
  [[anyang-backend-api#3-2. 채팅 인용 공지 스트림 계약 (신규, 제안, 미확정 — 확인 항목 22 반영)]]
  대로 `event:` 필드 유무로 나눈다). `event:` 없이 `data:`만 있는 줄은 기존처럼 DeepSeek
  OpenAI 호환 델타로 보고 AI 말풍선에 토큰 단위로 이어붙인다. `event: citations`가 붙은 블록의
  `data:` JSON 배열은 인용 공지 목록으로 파싱해 아래 인용 카드에 쓴다.
- **인용 공지 카드 (확인 항목 22 반영)**: backend 3-2절 계약에 맞춘다. 값은
  옮겨 적지 않고 링크한다.
  - **표시 필드**: 인용 이벤트 JSON 배열의 각 원소(`{ id, title, source_url, posted_at }`,
    [[anyang-backend-api#3-2. 채팅 인용 공지 스트림 계약 (신규, 제안, 미확정 — 확인 항목 22 반영)]])
    중 카드에는 `title`과 `posted_at`(날짜 형식은 제안)만 표시한다(제안) —
    `source_url`(원문 URL)은 카드에 직접 노출하지 않고 아래 링크 동작으로만 쓴다.
  - **위치**: 인용 이벤트는 대화당 1회, DeepSeek 청크보다 먼저 도착한다(backend 3-2절
    "전송 시점"). 수신 즉시 해당 AI 말풍선 **위쪽**에 카드 행("관련 공지" 레이블 + 카드
    리스트, 가로 스크롤 또는 세로 나열은 제안)을 먼저 그리고, 그 아래로 DeepSeek 토큰이
    스트리밍되며 말풍선 텍스트가 이어진다(제안).
  - **빈 목록 처리**: `data: []`(backend 3-2절 "빈 목록 처리" — 이벤트 자체는 생략되지
    않는다)를 받으면 "관련 공지" 카드 행 자체를 그리지 않는다(제안) — 빈 카드
    영역을 보여주는 대신 아예 생략해 말풍선만 표시한다.
  - **링크**: 카드 클릭 시 `/notices/[id]`(id는 인용 원소의 `id`)로 이동한다(제안) — 원문(`source_url`)은 카드에서 바로 열지 않고, 4절 공지 상세 화면에서 이미
    "새 탭으로 원문 이동" 링크를 제공하므로 카드는 내부 상세 페이지로만 연결한다(YAGNI —
    같은 원문 링크를 두 군데서 중복 제공하지 않는다).
- 대화 히스토리 목록 화면이 채택됐으므로([[anyang-service-scope]], user, 2026-09-27) `/chat`
  화면 진입 시에는 가장 최근 `conversation_id`를 이어서 쓰거나 새 대화를 시작하고(제안), 과거 대화를 다시 열려면 8절 목록 화면에서 선택해 들어온다
  ([[anyang-backend-api#3-1. 대화 히스토리 조회 — 채택]]).

### 3-1. 채팅 뒤로가기 시 대화·인용 유지 (신규, 확인 항목 60, 설계 draft)

문제: 인용 카드를 눌러 `/notices/[id]`로 갔다가 뒤로 오면 `chat-client.tsx`의 `messages` state가 사라지고(재마운트), 새 대화는 URL이 `/chat` 그대로라 서버에서도 되살릴 수 없다. 인용(`citations`)은 SSE 이벤트로만 오고 DB에 없다([[anyang-backend-api#3-2. 채팅 인용 공지 스트림 계약 (신규, 제안, 미확정 — 확인 항목 22 반영)]]). 해결은 ① 같은 탭 임시 보관(인용·스크롤 포함)과 ② URL에 `conversation_id`를 남겨 보관분이 없어도 본문을 서버에서 복원하는 두 겹이다. 사용자 결정은 프로젝트 문서 [[anyang-youth-policy-assistant#확인이 필요한 항목]] 60이 원본이고, 아래에서 `(미확정)`이 없는 것이 그 결정에서 직접 나온 값이다. API는 새로 필요 없다(기존 `GET /api/conversations/:id/messages`, [[anyang-backend-api#3-1. 대화 히스토리 조회 — 채택]]만 쓴다).

**결정에서 나온 값(확정)**: 보관소는 `sessionStorage`만(localStorage 금지), 키에 `conversation_id` 포함, 접근은 모두 try/catch(실패하면 ② 경로), 보관 대상은 messages(인용 포함)와 스크롤 위치, 복원 때 서버 재조회 없음, URL은 히스토리를 추가하지 않고 교체, 공지 상세 뒤로 버튼과 브라우저 뒤로가기 결과 동일, 다른 사용자·대화 섞임 방지, 로그아웃 시 정리, 보관분이 없으면 본문은 서버에서 복원(인용 카드 없음 수용).

**코드 구성 `(미확정)`**: 순수 함수는 새 `web/app/_lib/chat-snapshot.ts`, 화면은 기존 `chat-client.tsx`·`page.tsx`. 저장소 객체는 인자로 받아(테스트에서 가짜 저장소 주입) 브라우저 없이 단위 테스트한다.

1. **키 형식 `(미확정)`**: `anyang:chat:v1:{userId}:{conversationId}`. `userId`는 `page.tsx`가 `requireSession()` 결과의 `session.user.id`를 prop으로 내려준다(서버에서 이미 아는 값, 새 API 없음). 사용자가 다르면 키가 달라 다른 사용자의 보관분은 읽히지 않는다. `v1`은 형식을 바꿀 때 옛 보관분을 읽지 않게 하는 버전이다. `userId`가 없으면(타입상 가능) 보관·복원을 하지 않고 ② 경로만 쓴다.
2. **보관 형식 `(미확정)`**: JSON `{ v: 1, savedAt: <epoch ms>, messages: [{ role, content, citations? }], scrollTop: <number>, atBottom: <boolean>, streaming: <boolean> }`. `citations` 원소는 기존 `Citation`(`id`, `title`, `source_url`, `posted_at`) 그대로. 읽을 때 모양을 검사한다(`v`가 1, `messages`가 배열, 각 원소의 `role`·`content` 타입). 하나라도 어긋나면 그 보관분을 지우고 ② 경로로 간다(깨진 JSON도 같다).
3. **크기 상한 `(미확정)`**: 보관분 하나는 `messages`의 `content` 글자 수 합이 200,000자(약 400KB, UTF-16 기준)를 넘지 않게 한다. 넘으면 가장 오래된 메시지부터 버리고 최근 것을 남긴다(맨 앞이 assistant만 남지 않게 user/assistant 쌍 단위로 버린다). 같은 탭에 남기는 대화는 최대 10개이고(`(미확정)`), 넘으면 `savedAt`이 가장 오래된 보관분부터 지운다. `setItem`이 용량 오류로 던지면 다른 대화 보관분 중 가장 오래된 것을 지우고 한 번만 다시 시도하며, 그래도 실패하면 조용히 포기한다(② 경로가 이어받는다). 어떤 경우에도 오류를 화면에 띄우지 않는다.
4. **저장 시점 `(미확정)`**: 메모리의 최신 상태(`messages`, 스크롤 위치, `streaming`)를 ref에 늘 들고 있고, 쓰기는 아래에서만 한다. 스트림 델타마다 쓰면 큰 JSON을 초당 수십 번 직렬화하므로 델타는 마지막 변경 후 500ms 지나 한 번만 쓴다(`(미확정)` 값).
   - 즉시 쓰기: 사용자가 메시지를 보낸 직후, `citations` 이벤트 수신 직후, 스트림 완료(`sending`이 false가 될 때), 대화 id를 처음 받았을 때.
   - 이동 직전 쓰기: 컴포넌트 언마운트 정리 함수(공지 상세로 가는 `Link` 클릭과 `router.back()`이 모두 여기를 지난다), `pagehide`, `visibilitychange`가 `hidden`이 될 때(새로고침·탭 닫기·앱 전환). 스크롤 위치는 정리 함수 시점에 DOM이 이미 떨어져 있을 수 있으므로 `scroll` 이벤트에서 ref에 미리 담아 둔다(저장소에는 쓰지 않는다).
   - 대화 id가 아직 없으면(첫 메시지를 보내기 전, 또는 새 대화 직후 빈 상태) 쓰지 않는다.
5. **복원 순서**: 마운트 시 한 번만, 대화 id(prop `initialConversationId`)가 있을 때, 화면이 그려지기 전(`useLayoutEffect`)에: ① 보관분을 읽어 모양 검사를 통과하면 서버 조회 없이 `messages`를 채우고 스크롤을 복원한다. `streaming`이 true인 보관분만 아래 6번으로 간다. ② 보관분이 없거나 깨졌거나 저장소에 접근할 수 없으면 기존 코드 그대로 `GET /api/conversations/:id/messages`로 본문을 불러온다(인용 카드는 없다, 결정이 수용). ③ 서버 조회도 실패하면 기존 동작(빈 화면, 오류 문구 없음)을 유지한다. 복원이 끝나기 전에는 빈 대화 안내 문구("궁금한 청년정책을…")를 그리지 않는다(`(미확정)`: 새로고침 때 안내 문구가 한 번 깜박이는 것을 막으려는 값). 이 한 번의 복원이 끝난 뒤에는 prop이 바뀌어도 다시 불러오지 않는다(아래 7번의 위험 때문에 `loadedIdRef`로 "이미 이 id를 쓰고 있다"를 기록한다).
6. **스트리밍 중 이동 후 복귀 `(미확정)`**: 보관분의 `streaming`이 true인 채 돌아온 경우(이동·새로고침이 답변 도중이었다). 공지 상세로의 화면 이동(SPA)은 요청을 끊지 않으므로 서버는 답변을 끝까지 받아 저장하고, 새로고침·탭 닫기는 요청을 끊지만 서버는 그때까지 받은 부분을 저장한다(backend 문서 3-3-2절의 "부분 답변 저장(확정, 43-b)" 단락, [[anyang-backend-api]]). 그래서 이 경우만 서버를 한 번 조회한다. 서버 메시지 수가 보관분 이상이면 서버 목록으로 바꾸되, 같은 위치의 assistant 메시지에 보관분의 `citations`를 옮겨 붙인다(인용은 서버에 없다). 서버 메시지 수가 보관분보다 적으면(서버가 아직 답변을 못 남김) 보관분을 그대로 보여 주고 마지막 답변 아래에 한 줄 "답변이 중간에 멈췄을 수 있어요. 새로고침하면 저장된 내용을 보여줘요."(`text-meta` ink-3, 문구 `(미확정)`)를 더한다. 복원 직후에는 `streaming: false`로 다시 쓴다. 되돌아와도 끊긴 스트림을 이어서 받지는 않는다(되돌린 화면에서 새 요청을 자동으로 보내지 않는다).
7. **URL 동기화와 `router.replace` 시점 `(미확정, 결정 문구와 다름 — 사용자 확인 필요)`**: 사용자 결정은 "`router.replace`로 `/chat?conversation_id=…`, 히스토리 추가 없음"이다. 응답 헤더 `x-conversation-id`는 스트림 본문보다 먼저 오므로 헤더를 읽는 즉시 URL을 맞추면, 답변 도중에 공지로 가거나 새로고침해도 URL이 이미 대화를 가리킨다. 그런데 이 시점에 `router.replace`를 부르면 두 가지 위험이 있다. (가) 검색 파라미터가 바뀐 이동이라 서버 컴포넌트 `page.tsx`가 다시 그려지고 `initialConversationId` prop이 `null`에서 새 id로 바뀐다 — 지금 코드의 `useEffect([initialConversationId])`가 그때 서버 대화를 불러와 스트리밍 중인 `messages`를 덮어쓴다(5번의 `loadedIdRef`로 막는다). (나) Next.js 16.3.6 코드에서 페이지 세그먼트의 캐시 키에 검색 파라미터가 포함된다(`create-router-cache-key.js`의 `__PAGE__?...` 주석). 공식 문서의 `router.bfcacheId` 설명("검색 파라미터만 바뀌는 이동에서는 같은 값")은 상태가 유지된다는 쪽이지만, 이 프로젝트에서 스트리밍 도중의 `router.replace`가 재마운트나 스트림 중단을 일으키지 않는지는 문서·소스 읽기로 확정하지 못했고 실행해 보지 못했다. 그래서 이 문서는 두 안을 적고 하나를 제안한다.
   - 제안 안 A: 헤더를 받는 즉시 `window.history.replaceState(null, "", "/chat?conversation_id=…")`를 쓴다. Next.js 문서는 이 네이티브 호출이 라우터와 연동되고(`usePathname`·`useSearchParams`와 동기화) 서버 요청이나 재렌더를 일으키지 않는다고 설명한다(`01-getting-started/04-linking-and-navigating.md`의 "Native History API"). 히스토리 항목은 추가하지 않고 교체하며 스트림은 영향이 없다. 결정 문구의 "router.replace"와 수단만 다르고 결과(교체, 추가 없음)는 같다.
   - 대안 B: 결정 문구대로 `router.replace("/chat?conversation_id=…", { scroll: false })`를 쓰되 스트림이 끝난 뒤에 부른다. 이 안은 답변 도중 이동·새로고침 때 URL에 id가 아직 없어(첫 대화) 그 구간은 보관분만으로 복원되고(키는 id가 있어야 하므로 id 없이 이동하면 복원 불가), 답변이 끝난 뒤 재렌더가 일어나도 상태가 사라지지 않는지는 구현 때 실제로 확인해야 한다.
   - 이미 id가 있는 대화(`?conversation_id=…`로 들어왔거나 한 번 교체한 뒤)는 URL이 이미 맞으니 아무것도 하지 않는다. 구현은 안 A를 쓰고, 안 A로 `useSearchParams`·히스토리 뒤로가기(교체된 항목으로 돌아오면 `?conversation_id=…`로 `page.tsx`가 다시 그려져 prop이 채워진다)가 의도대로 되는지 실행으로 확인한다. 안 A가 의도대로 안 되면 안 B로 바꾸는 것은 설계 변경이므로 구현 중에 멈추고 보고한다.
8. **스크롤 복원**: 스크롤은 창이 아니라 메시지 영역(`role="log"` div, 기존 `scroller` ref)이 한다. 그래서 브라우저·Next의 기본 스크롤 복원이 적용되지 않으므로 직접 한다. 보관 시 `scrollTop`과 `atBottom`(`scrollHeight - scrollTop - clientHeight`가 `(미확정)` 8px 이하)을 함께 담는다. 복원은 `messages`가 채워진 직후 레이아웃 시점에 한 번만: `atBottom`이 true이면 맨 아래로, 아니면 보관한 `scrollTop`으로 둔다. 기존 "메시지 개수가 바뀌면 맨 아래로" 효과가 복원 때 덮어쓰지 않도록, 복원으로 인한 첫 변화는 건너뛴다(`restoredRef`). 인용 카드 때문에 높이가 달라져 `scrollTop`이 어긋날 수 있으나 보관분이 있을 때만 해당하고 수용한다. 서버에서 복원한 경우(② 경로)에는 스크롤 값이 없으므로 기존처럼 맨 아래로 간다.
9. **공지 상세 뒤로 버튼 `(미확정 아님 — 기존 코드 사실)`**: `notice-detail.tsx`의 "‹ 공지" 버튼은 고정 링크가 아니라 `window.history.length > 1`이면 `router.back()`, 아니면 `/notices`로 `router.push`한다. 브라우저·휴대폰 뒤로가기도 같은 히스토리 항목으로 돌아간다. 7번으로 채팅 항목의 URL이 `/chat?conversation_id=…`로 교체되어 있으므로 두 방법 모두 같은 URL로 돌아오고, 같은 복원 흐름(5번)을 지나 결과가 같다. 이 문서에서는 `notice-detail.tsx`를 바꾸지 않는다. 푸시 알림으로 공지 상세에 바로 들어온 경우(히스토리 없음)는 `/notices`로 가며 채팅과 무관하다. 인용 카드의 `Link`는 새 항목을 쌓는 `push` 이동이라 1→5번 순차 열람(카드 1 → 뒤로 → 카드 2 …)이 각각 같은 방식으로 복원된다.
10. **새 대화 시작 버튼**: 기존 동작(`conversationIdRef = null`, `messages` 비움, 오류 비움, `router.push("/chat")`)에 더해, 이전 대화의 보관분은 지우지 않는다(뒤로가기로 이전 대화로 돌아올 수 있고, 대화 기록 화면에서 다시 열 때도 같은 탭이면 인용이 남는다). 비운 직후 빈 상태는 보관하지 않는다(대화 id가 없으니 4번에 따라 쓰지 않는다). 새 대화에서 첫 메시지를 보내면 새 id로 새 보관분이 생긴다. 답변 수신 중에는 지금처럼 버튼이 동작하지 않는다.
11. **로그아웃·탈퇴 정리 `(미확정)`**: 같은 접두사(`anyang:chat:v1:`)의 보관분을 모두 지우는 `clearAllChatSnapshots(storage)`를 로그아웃 처리 세 곳에서 `signOut` 직후 부른다: `settings/profile-section.tsx`의 `handleLogout`, `suspended/suspended-actions.tsx`의 `handleLogout`, `settings/account/account-client.tsx`의 탈퇴 성공 후 `/login` 이동 직전. 키에 `userId`가 들어 있어 정리가 빠져도 다른 사용자에게 읽히지는 않지만, 같은 탭에 개인 대화 내용이 남지 않게 하는 이중 장치다. 세션이 만료돼 로그인 화면으로 밀려나는 경우는 정리하지 않는다(탭을 닫으면 사라지고 키로 구분된다, 수용).
12. **실패 시 ② 경로**: 저장소 접근 불가(사생활 보호 모드·권한), 용량 초과, JSON 깨짐, 모양 검사 실패, 사용자 불일치로 보관분이 없는 모든 경우는 보관분이 없는 것과 같게 다룬다 — 서버에서 본문을 복원하고 인용 카드만 없다. 저장 중 실패는 조용히 무시한다.
13. **바꾸는 파일 `(미확정)`**: 새 `web/app/_lib/chat-snapshot.ts`, 새 `web/test/frontend-chat-snapshot.test.ts`, `web/app/(tabs)/chat/chat-client.tsx`, `web/app/(tabs)/chat/page.tsx`(prop `userId` 추가), `web/app/(tabs)/settings/profile-section.tsx`, `web/app/suspended/suspended-actions.tsx`, `web/app/(tabs)/settings/account/account-client.tsx`. `notice-detail.tsx`, `app/api/**`, `lib/**`, `db/**`는 바꾸지 않는다.

### 5. 알림 설정 (`/settings/notifications`)

> 2026-10-03 청안 개정: 화면 구성·외형은 "청안 디자인 적용 화면 스펙"의 알림 절이 우선한다. 권한 요청·구독·재구독 흐름은 아래 그대로다.

- 구성: on/off 토글(`enabled`), 알림 시각 자유 입력. 사용자별 자유 시각 설정으로
  **확정**됐으므로([[anyang-service-scope]], user, 2026-09-27) 고정 선택지(라디오/드롭다운)는
  더 이상 고려하지 않는다. 입력 컴포넌트는 네이티브 `<input type="time">` 제안(YAGNI, 커스텀
  타임피커 불필요). 저장 값은 `notify_time`(time)
  ([[anyang-database-schema#notify_settings (항목 범위·시간대·컬럼 타입 모두 확정)]]).
- 조회/저장: `GET/PUT /api/notify-settings`
  ([[anyang-backend-api#2-2. 알림 설정 — 채택 (사용자별 자유 시각 + on/off)]]).
- **알림 대상 범위 안내**(제안 문구 — backend `enabled_at` 반영,
  [[anyang-backend-api#2-2. 알림 설정 — 채택 (사용자별 자유 시각 + on/off)]]): 알림을 켠
  시각(`enabled_at`) 이후 수집된 공지만 알림 대상이 된다. 화면에 "알림을 켠 시점 이후에
  올라온 공지부터 알려드려요"(제안 문구) 같은 안내를 토글 근처에 덧붙인다 — 토글을
  껐다가 다시 켜면 그 시점부터 다시 계산된다는 점도 같은 문구로 함께 전달한다(제안).
- **PWA 푸시 권한 요청 흐름**(제안): 이 화면에서 토글을 켜는 시점에 브라우저
  `Notification.requestPermission()` 요청 → 허용되면 서비스워커의 `PushManager.subscribe()`로
  구독 정보를 받아 `POST /api/push/subscribe`([[anyang-backend-api#8. Web Push (VAPID)]])
  호출. 거부되면 토글을 다시 꺼진 상태로 되돌리고 "브라우저 알림 권한이 필요합니다" 안내
  (제안 문구). 토글을 끄면 `DELETE /api/push/subscribe` 호출(제안 — 기기별 구독
  해지인지 계정 전체 알림 비활성인지는 `enabled` 플래그와 별개로 정리, 제안).
- **도메인 변경 시 재구독 유도**(제안): origin이 바뀌면 기존 Web Push 구독이
  무효화되므로([[anyang-backend-api#12-1. 커스텀 도메인 연결 절차 (환경 전환 아님, 배포 origin만 교체) — 제안, 미확정]]),
  이 화면 진입 시 구독 상태를 확인해(제안 — 서비스워커 `PushManager.getSubscription()`이
  null인데 `enabled`가 true면 재구독 필요로 판단) 배너/알림으로 "알림을 다시 켜주세요" 안내
  후 재구독 흐름(위 권한 요청과 동일)을 다시 태운다.

### 11. 공지 수집 관리 (`/admin/collect-runs`)

- `GET /api/admin/collect-runs`([[anyang-backend-api#13-1. 공지 수집 관리]]) 결과를 최신순
  테이블/리스트로 표시(제안 컬럼: 실행 시각, 트리거 종류(수동/스케줄), 성공 여부,
  수집 건수, 오류 요약 — [[glossary#수집 실행 기록]] 기준). 페이지네이션 방식은 backend와
  동일하다(제안).
- 수동 수집 실행 버튼: `POST /api/admin/collect-runs` 호출. 이 호출은 최대 300초 걸릴 수
  있으므로([[anyang-backend-api#13-1. 공지 수집 관리]]) 클릭 즉시 버튼을 비활성화하고 "수집
  실행 중..." 진행 상태 표시(스피너, 제안)를 두며, 응답이 올 때까지(최대 300초) 페이지 이동을
  막지 않되 다른 수동 실행 재클릭은 막는다(제안 — 타임아웃 시 오류 메시지 문구도
  제안). 완료되면 목록을 새로고침한다.
- **56 개정 — 수동 수집 버튼과 실행 이력 표시 (신규)**: 운영에서는 직접 수집 스위치 `DIRECT_COLLECT_ENABLED`가 꺼져 있어 `POST`가 410 `DIRECT_COLLECT_DISABLED`를 받고, 이력 표에는 보드 받기 API가 남긴 행이 쌓인다([[anyang-board-collector]] C-4·D, [[anyang-backend-api#13-1. 공지 수집 관리]]). 1번~2번이 이 항목을 대신해 위 두 불릿(수동 수집 버튼·이력 컬럼)에 우선한다.
  1. **버튼: 숨기지 않고 410 응답 때 안내만 띄운다 (제안)**. 서버가 스위치 상태를 미리 알려 주는 API는 없다. `GET /api/admin/collect-runs`는 행 배열만 돌려주고 스위치 값이 없다. 새 API나 응답 필드 추가(backend 설계 변경) 없이 되는 안을 골랐다. 검토한 세 안:
     | 안 | 장단점 |
     |---|---|
     | (가) 항상 숨김 | 스위치를 켜는 경우(앱을 보드로 옮길 때, [[anyang-deployment-portability]])에 코드를 고쳐야 한다. 서버가 켜진 상태인지 화면이 알 수 없다. |
     | (나) 비활성 + 항상 안내 | 스위치가 켜진 환경에서 안내가 거짓이 된다. 켜졌는지 알려면 새 API가 필요하다. |
     | **(다) 보이되 410이면 안내 (채택안)** | 새 API 없음. 켜진 환경은 지금 동작 그대로. 꺼진 환경은 한 번 눌러야 안내가 뜨는 불편이 있고, 눌러도 서버는 인증 뒤 410만 돌려주므로 수집 호출·`collect_runs` 행은 생기지 않는다([[anyang-board-collector]] D). |
     - 410 응답 본문의 `error`가 `DIRECT_COLLECT_DISABLED`일 때만 안내한다. 다른 410이나 본문이 없는 경우는 기존 일반 오류 문구("수집 실행 중 오류가 발생했습니다.")로 처리한다(약속된 코드만 해석).
     - 안내 문구(제안): "이 서버에서는 직접 수집이 꺼져 있어요. 공지 수집은 보드가 자동으로 합니다. 결과는 아래 실행 이력에서 확인하세요." 오류 색(`error-text`)이 아니라 일반 안내(`hint-text`, `role="status"`)로 표시한다 — 고장이 아니기 때문이다.
     - 안내가 뜬 뒤에는 이 페이지를 떠나기 전까지 버튼을 비활성화(`disabled`)하고 같은 안내를 버튼 옆에 유지한다. 새로고침하면 다시 눌러 볼 수 있다(상태를 저장하지 않는다, YAGNI).
     - 기존 동작은 그대로: 클릭 즉시 비활성·"수집 실행 중..." 표시, 403은 관리자 공통 가드 처리, 그 밖 실패는 일반 오류 문구. 409 `ALREADY_RUNNING`·`ROBOTS_DISALLOWED`의 전용 문구는 이번 범위가 아니다(현재도 일반 문구).
     - 대안이 필요해지면(켜졌는지 미리 알고 싶을 때): `GET` 응답에 스위치 값을 더하는 것은 backend 설계 변경이라 이번에 요청하지 않는다. 미해결 질문으로만 올린다.
  2. **이력 표 표시 (제안)**. 서버가 주는 값은 그대로 두고 화면에서만 사람이 읽는 글로 바꾼다. 값이 아래 표에 없으면 **원문 그대로** 보인다(지어내지 않는다). 변환은 순수 함수 `describeRun`으로 분리한다(작업 단위 [[anyang-frontend-tasks#공지 수집 관리 — 보드 수집 이력 표시 (확인 항목 56, 신규, 설계 draft, 구현은 재승인 후)]] K1).
     | 컬럼 | 서버 값 | 표시 (제안) |
     |---|---|---|
     | 실행 시각 | `started_at` | 지금과 같음(`toLocaleString`) |
     | 실행 방식 | `trigger_type` | `manual` → "수동", `scheduled` → "자동", 그 밖 → 원문. 보드 행은 backend가 `scheduled`로 남긴다([[anyang-board-collector]] C-4). 보드 행과 서버 스케줄 행을 이 값으로는 구별할 수 없다 — 서버 스케줄 수집은 등록된 적이 없고([[anyang-board-collector]] D) 구별 값은 backend 문서에 없으므로 "보드"라고 쓰지 않는다. |
     | 상태 | `status` | `success` → "성공", `failed` → "실패", `running` → "실행 중", 그 밖 → 원문 |
     | 수집 건수 | `collected_count` | 숫자면 "새 글·바뀐 글 N건", null이면 "-". 이 값은 `created`+`updated` 합계다([[anyang-board-collector]] C-2). "받은 총 건수"가 아니다. |
     | 결과 설명 | `error_summary` | 아래 표 |

     - 결과 설명은 `error_summary`의 **첫 단어(공백 앞)**가 아래 코드와 같을 때 문구로 바꾼다. 바뀐 경우에도 원문을 작은 글씨로 함께 둔다(`<small>`, 예: `ip_blocked`) — 종류 같은 덧붙은 정보와 알 수 없는 변형이 사라지지 않게 하기 위함이다.
     | 코드 (backend 문서에 적힌 것만) | 표시 문구 (제안) |
     |---|---|
     | `ip_blocked` | "안양시 사이트가 접속을 막았어요(IP 차단). 새 공지를 가져오지 못했습니다." |

     | `parse_failed` | "일부 공지의 본문을 읽지 못해 건너뛰었어요." |
     | `fetch_failed` | "안양시 사이트 요청이 실패했어요(오류 또는 시간 초과)." |

  클릭 시 앱 포커스/열기(`notificationclick`)만 담당한다(제안).
  **`url` 처리(2026-10-04, 확인 항목 58, `(미확정)`)**: 테스트 알림 payload `{ title, url }`
  ([[anyang-backend-api#8-1. 테스트 알림 (신규, 2026-10-04, 확인 항목 58)]])에서도 클릭 이동이
  되도록 `web/public/sw.js`의 `parsePushPayload`만 고친다. `payload.url`이 문자열이고 `/`로
  시작하며 `//`로 시작하지 않을 때만 그 값을 이동 대상으로 쓴다(같은 출처 상대 경로만 허용).
  frontend가 backend 문서의 조건에 하나를 더 막는다: `/\`로 시작해도 쓰지 않는다(브라우저가
  `\`를 `/`로 읽어 `/\evil.com`이 `//evil.com`과 같이 외부 주소가 되기 때문). 조건에 안 맞으면 기존대로
  `notice_id` → `/notices/[id]` → 기본 `/notices` 순서다. `url`과 `notice_id`가 함께 오면
  `url`이 먼저다(공지 알림은 `url`을 보내지 않으므로 기존 동작은 변하지 않는다). `notificationclick`
  핸들러(`data.url` 사용, 열린 창이 있으면 포커스, 없으면 `openWindow`)와 `push` 핸들러는 바꾸지
  않는다. 필드명 `url`은 backend 문서와 같아 바꾸지 않는다. 오프라인 캐싱
  전략(프리캐시 자산 목록 등)은 이번 요청 범위에 없다 — 요청되지 않은 오프라인 지원까지
  만들지 않는다(YAGNI). 필요해지면 별도 요청으로 재설계.
- 서비스워커 등록 위치(제안): 루트 레이아웃 클라이언트 컴포넌트에서

- VAPID 공개키는 서버 환경변수 `VAPID_PUBLIC_KEY`([[anyang-backend-api#9. 환경변수 목록]])를

#### 2. 공지 목록 (청안 NoticesScreen → `/notices`)

- 파일: `app/(tabs)/notices/notices-list.tsx`, `NoticeRow`는 새 `ui/notice-row.tsx`.
- 구성: 머리(좌 "청안" `type-title` 제목 글꼴, 우 오늘 날짜 `9월 29일 화요일` mono ink-3) → `h1`(`type-display`): 관심사가 1개 이상이면 "나에게 맞는 공지", 0개면 "최근 공지" → 설명 줄(`type-body-sm` ink-2): 있으면 "대화에서 모인 관심사 N개와 가까운 순서예요", 0개면 "아직 대화 전이라 최신순이에요. 대화할수록 더 잘 맞춰져요." 우측에 링크 "관심사 보기"(`/settings`로 이동, 높이 44) → 아래 2px `ink` 선(`--border-strong`, 목록 시작선) → 공지 행 목록.

  - **고정 공지(`is_pinned`)**: 제목 앞에 별표 아이콘 + 굵은 제목. 구체 값은 다음과 같다: 별표는 `accent` 색 16px(제목 첫 줄 높이에 맞춰 위쪽 정렬, 제목과 간격 6px), 고정 공지 제목은 `font-semibold`(토큰 `type-title` 기본 600), 일반 공지 제목은 `font-medium`(500)으로 낮춰 대비를 만든다. 글꼴 굵기가 400·500·600뿐이라([[anyang-cheongan-design-adoption]] 5절) 700은 쓰지 않는다. 일반 공지 굵기를 낮추면 `/conversations` 행과 달라지므로 `NoticeRow`만 제목 굵기를 바꾸고 `ListRow` 기본(600)은 그대로 둔다.
  - **별표 아이콘**: 청안 `Icon.tsx`에 별이 없다. `ui/icon.tsx`에 `star`를 하나 더 추가한다(같은 선 아이콘 규격, 채움 `currentColor`). 청안 팀 자산이 아니라 새로 그리는 것이므로 승인 때 확인한다. 글자 `★`로 대체하는 안은 글꼴에 따라 모양이 달라 채택하지 않는다.
  - **"이미지" 칩(`image_count > 0`)**: 날짜 오른쪽에 둔다. `image_count`의 정의(본문 이미지와 이미지 첨부 합산)는 [[anyang-backend-api#2-1. 추천 공지 피드·상세 (frontend 조율, 2026-09-27)]]를 따른다. 글자 `type-meta`(12px) ink-2, 테두리 1px `rule`, 면 채움 없음(청안 규칙), 모서리 `radius-badge`(4px, 토큰 주석이 "본문 이미지 표시"용), 가로 패딩 6px. 글자는 사용자 표기 그대로 "이미지"이고 개수는 보이지 않는다. `image_count`가 0이거나 필드가 없으면 칩을 그리지 않는다.
  - **접근성 이름**: 별표 아이콘은 `aria-hidden="true"`이고, 같은 링크 안 제목 앞에 `sr-only` 글자 "고정 공지, "를 둔다(링크의 읽히는 이름이 "고정 공지, 제목..."이 된다). 칩은 보이는 글자 "이미지"가 그대로 읽히므로 `aria-label`을 따로 주지 않는다(주면 보이는 글자를 덮어쓴다). 별표·칩 모두 색만으로 뜻을 전하지 않는다(별 모양과 글자가 있다).
- 데이터: `GET /api/notices/recommended?page=N`(`{id, title, excerpt, posted_at, is_pinned, image_count}`, 필드 계약은 [[anyang-backend-api#2-1. 추천 공지 피드·상세 (frontend 조율, 2026-09-27)]], 응답은 `Cache-Control: no-store`), 관심사 개수는 `GET /api/preferences` 응답 배열 길이. 두 호출은 독립이고 preferences 호출이 실패하면 머리 제목은 "최근 공지", 설명 줄은 생략한다.
- 이 화면에서 게시일을 표시하는 것은 시안의 구성 요소를 그린 것이다(47(c)③ 처리를 따로 한 것이 아니다). 관심사 0개일 때 서버가 최신순으로 돌려주는지는 이 설계가 확인하지 못했다([[anyang-cheongan-design-adoption]] 49 조사에서도 못 확인) — 문구는 서버 동작과 맞는지 구현 시 확인한다.
- 더 보기: 기존 "더 보기" 버튼 방식(`page` 증가)을 유지하고 버튼은 보조(secondary) 모양. 로딩 `불러오는 중...`, 오류 `공지를 불러오지 못했습니다.`, 목록 0건 `아직 추천할 공지가 없어요.`(모두 현재 문구).
- 오늘 날짜 표시는 서버·클라이언트 불일치(hydration)를 피하려고 마운트 뒤에 계산한다(한국 시간 기준).
- **정렬과 고정 공지 표시**: 정렬은 서버가 정한다. "최근 공지"(관심사 0개, 선호 없음)만 고정 공지를 위로 올리고, 추천 정렬은 유사도 순서를 유지한 채 별표만 표시한다(사용자 확정, 2026-10-04, 55-k·55-d). 화면은 응답 순서를 그대로 그리고 `is_pinned`가 true인 행에 별표만 붙인다.
- **최신성(확정: 탭 복귀·재진입 시 재조회, Realtime 없음)**: `notices-list.tsx`가 아래 때 1페이지를 다시 불러온다.
  - 트리거: `document`의 `visibilitychange`에서 `document.visibilityState === "visible"`이 될 때, 그리고 `pageshow` 이벤트의 `event.persisted`가 true일 때(뒤로가기 캐시에서 복원된 경우). 홈 화면 앱(PWA)을 다시 열면 보통 `visibilitychange`가 오므로 "앱 재진입"은 이것으로 덮는다. 다른 화면에 갔다가 `/notices`로 돌아오는 것은 컴포넌트가 새로 마운트되어 이미 다시 불러온다.
  - 재조회 빈도 제한: 마지막 성공 조회 후 30초 이내면 생략하고, 조회 중에 또 트리거가 오면 무시한다. 판정은 순수 함수 `shouldRefetch(lastFetchedAt, now, minGapMs)`로 분리해 단위 테스트한다. 30초는 확정값이다(10분마다 수집하는 글이라 30초 안에 바뀔 일이 드물다).
  - 반영 방식: 화면을 깜빡이지 않는 조용한 갱신이다. "불러오는 중..."과 오류 안내를 띄우지 않고, 실패하면 기존 목록을 그대로 둔다. 가져온 1페이지를 맨 앞에 두고, 이미 불러온 나머지 항목 중 같은 `id`는 뺀 채 이어 붙인다(더 보기로 쌓은 항목과 스크롤 위치를 유지하고, 새 글로 밀려난 항목의 중복을 막는다). 서버에서 숨김 처리된 글은 이 병합으로는 사라지지 않고 목록을 새로 열 때 사라진다. `page` 상태는 바꾸지 않는다.
  - 관심사 개수(`GET /api/preferences`)는 다시 부르지 않는다(공지 수집과 무관). 공지 상세는 다시 부르지 않는다(한 건이고 다음 열람 때 보이면 충분하다).
  - 서버 쪽 캐시는 backend가 `no-store`로 막으므로 화면은 `fetch`에 따로 캐시 옵션을 주지 않는다.

#### 3. 공지 상세 (청안 NoticeDetailScreen → `/notices/[id]`)

- 파일: `app/(tabs)/notices/[id]/notice-detail.tsx`.
- 구성: 상단 "‹ 공지" 되돌아가기(높이 44, `chevron-left` + "공지", 히스토리가 있으면 `router.back()`, 없으면 `/notices`로 — 푸시 알림으로 바로 연 경우 대비) → 본문 영역(스크롤): 제목 `type-display-sm`(제목 글꼴) → "게시 YYYY.MM.DD"(mono ink-3, `posted_at`이 null이면 줄 생략) → `rule` 구분선 → 본문 `type-body`, `whitespace-pre-line`, 본문 속 http(s) 주소는 새 탭 링크(밑줄, `rel="noopener noreferrer"`)로 바꾼다 → 맨 아래 고정 바(윗선 `rule`): "원문 보기 ↗"(기본 큰 버튼 `h-button-lg`, 전체 폭, `aria-label="원문 보기, 새 창에서 열림"`, `source_url`을 새 탭으로).

- **첨부 파일 영역(2026-10-04, 확인 항목 55)**: 본문 아래, 같은 스크롤 영역 안에 둔다. `attachments`(`[{name, url}]`, 없으면 `[]`, [[anyang-backend-api#2-1. 추천 공지 피드·상세 (frontend 조율, 2026-09-27)]])를 쓴다.

  - 접근성: 목록은 `<ul>`, 소제목은 `aria-labelledby`로 목록에 연결한다.
- 하단 고정 바 버튼의 글자와 `aria-label`을 "원문 페이지에서 보기"·"원문 페이지에서 보기, 새 창에서 열림"으로 바꾼다(기존 "원문 보기" 대체). 링크는 `target="_blank"`, `rel="noopener noreferrer"`(요청한 `noopener`에 `noreferrer`를 더한 것으로 52 설계 그대로이며, 안양시 사이트에 우리 주소가 전달되지 않게 한다).
- `source_url`은 `http://`·`https://`로 시작할 때만 링크로 그린다(아니면 원문 보기 버튼을 그리지 않는다) — 수집 데이터가 외부에서 오므로 방어한다. 기존 4절의 "iframe 임베드 없음"은 그대로.
- 상태: 404(`존재하지 않거나 숨김 처리된 공지입니다.` — 시안의 "이 공지는 더 이상 볼 수 없어요."와 의미가 같아 시안 문구로 바꾼다) + "공지 목록으로" 보조 버튼. 오류 `공지를 불러오지 못했습니다.`. 이미지 안내 상자(`ImageNote`)는 이번에도 만들지 않는다(사용자 결정은 배지·별표까지).
- 하단 탭 바: 모바일·태블릿에서는 숨기고 "원문 보기" 바가 그 자리를 쓴다. 데스크톱은 사이드바 유지, 고정 바는 콘텐츠 열 폭 안.

#### 4. 알림 (청안 AlertsScreen → `/settings/notifications`)

- 파일: `app/(tabs)/settings/notifications/notifications-client.tsx`(푸시 구독·권한·재구독 로직은 그대로, 외형만 시안으로).

  - 행 1 "새 공지 알림": 아래 상태 줄(`type-label` ink-2) + 오른쪽 `Switch`. 상태 줄: 켜짐 "매일 오전 8:00에 보내요"(실제 `notify_time`을 "오전/오후 h:mm"으로), 꺼짐 "꺼져 있어요", 이 기기에서 켤 수 없음 "홈 화면에 추가한 뒤 켤 수 있어요".
  - 행 2 "받을 시각": 오른쪽에 네이티브 `<input type="time">`(높이 44, 값 `notify_time`). 시안의 시각 선택 시트는 만들지 않는다. 켤 수 없는 상태에서는 비활성.
- 켜진 상태(설치된 기기)에서 "이렇게 보내요" 소제목 + 규칙 목록 4줄(시안 문구, 각 줄 `rule` 선): 알림을 켠 뒤 올라온 공지만 보내요 / 같은 공지는 한 번만 보내요 / 정한 시각에서 5분 안에 도착해요 / 아직 대화를 하지 않았다면 알림이 가지 않아요. 네 줄은 [[anyang-backend-api]]의 알림 동작(켠 뒤 수집분만, 중복 방지, 5분 창, 선호 없으면 발송 안 함)과 맞는다고 문서 기준으로 읽었으나 실제 발송 동작은 확인하지 못했다. 기존 5절의 "알림을 켠 시점 이후에 올라온 공지부터 알려드려요" 안내는 이 첫 줄이 대신한다.
- 이 기기에서 켤 수 없는 상태(iOS 브라우저 탭에서 열림, 홈 화면에 추가 전): 스위치·시각 입력 비활성 + 상태 줄 + 안내 상자("iPhone에서는 홈 화면에 추가해야 알림을 받을 수 있어요", 순서 1~3: Safari 공유 버튼 → '홈 화면에 추가' → 홈 화면의 청안을 열고 이 화면에서 알림 켜기, "iOS 16.4 이상에서 받을 수 있어요"). 판정은 클라이언트에서 한다: iOS 기기이면서 `display-mode: standalone`이 아님. 현재 코드에는 이 판정이 없어 새로 만든다. iPadOS는 Mac처럼 보이는 사용자 에이전트를 보내므로 터치 지점 수도 함께 본다 — 판정이 틀릴 수 있는 한계가 있어 판정 함수에 단위 테스트를 둔다. iOS가 아니면 안내 상자·비활성 상태는 나오지 않는다. 안내 상자의 "청안"은 시안 문구이고 manifest 앱 이름은 `안양비서`라 이름이 어긋난다 — 어느 쪽에 맞출지 확인.
- 그대로 유지: 권한 요청 → `PushManager.subscribe` → `POST /api/push/subscribe`, 거부 시 토글 되돌림 + "브라우저 알림 권한이 필요합니다.", 끄면 `DELETE /api/push/subscribe`, 구독 없이 `enabled`이면 재구독 배너 + 흐름. 배너와 오류 문구는 `bg-surface` + `rule` 테두리 상자와 `text-danger`로 입힌다.
- 뺀 것: "받는 기기" 목록(구독 조회 GET 없음).
- **테스트 알림 보내기(2026-10-04, 확인 항목 58)**: 파일은 같은 `notifications-client.tsx`, 호출 결과를 문구로 바꾸는 순수 함수는 새 `app/_lib/test-notify.ts`의 `describeTestResult(status, body)`. 호출은 `apiFetch("/api/notify-settings/test", { method: "POST" })`(body 없음, 계약은 [[anyang-backend-api#8-1. 테스트 알림 (신규, 2026-10-04, 확인 항목 58)]]). 403 정지·재동의는 `apiFetch`가 이미 `/suspended`·`/consent`로 보내므로 따로 처리하지 않는다. 사용자가 확정한 것은 "버튼 + 결과 안내 3가지(성공 n대 / 구독 없음 / 잠시 후 다시 시도) + 기존 스타일"이고, 아래 값은 모두 `(미확정)`이다.
  - 위치·표시 조건 `(미확정)`: 스위치·시각 `SettingsGroup` 바로 아래, 오류 상자 위. 알림이 켜져 있고(`enabled`) 이 기기에서 켤 수 있을 때(`installRequired`가 아닐 때)만 그린다. 꺼져 있으면 보낼 대상이 없어 결과가 항상 "구독 없음"이라 보이지 않게 했다. 켜져 있어도 이 기기 구독이 끊긴 경우(`needsResubscribe`)와 서버 구독이 0인 경우는 있으므로 "구독 없음" 안내는 필요하다. 이 안내는 재구독 배너와 같은 화면에서 읽히므로 문구가 "알림 다시 켜기"와 맞아야 한다.
  - 모양 `(미확정)`: 소제목 "알림 확인"(`text-label font-semibold text-ink-2`, "이렇게 보내요"와 같은 소제목 모양) → 보조 안내 한 줄 "지금 알림이 오는지 확인해 보세요."(`text-body-sm ink-2`) → `Button` secondary "테스트 알림 보내기"(기본 높이 `h-control`) → 결과 줄. 새 컴포넌트·아이콘은 만들지 않는다(기존 `Button`, 청안 토큰).
  - 진행 중 `(미확정)`: 요청이 나간 뒤 응답이 올 때까지 버튼을 `disabled`로 하고 글자를 "보내는 중..."으로 바꾸며 `aria-busy="true"`를 준다. 서버가 동시 두 요청을 막지 못하므로 이 비활성이 중복 전송을 막는 유일한 장치다([[anyang-backend-api#8-1. 테스트 알림 (신규, 2026-10-04, 확인 항목 58)]] 한계 절). 누를 때 이전 결과 줄은 지운다.
  - 결과 줄: 버튼 아래, `role="status"`(스크린리더가 읽음), 글자 `text-body-sm`. 성공·안내는 `ink-2`, 오류성은 `text-danger`. 색만으로 뜻을 전하지 않는다(문구가 있음). 결과 줄은 다음 테스트나 화면 이동 때까지 남는다(자동으로 사라지지 않음).
  - 문구와 분류 `(미확정)`. `describeTestResult`의 입력은 응답 상태와 파싱된 body(없거나 깨지면 `null`), 출력은 `{ kind, message }`이다.

    | 조건 | kind | 문구 | 사용자 확정 3가지와의 관계 |
    |---|---|---|---|
    | 200, `success_count ≥ 1` | `success` | "1대에 테스트 알림을 보냈어요." (n대) | "성공 n대" 그대로 |
    | 200, `success_count ≥ 1`, `failed_count ≥ 1` | `success` | "n대에 보냈어요. m대는 보내지 못했어요." | 성공 안내에 실패 수를 덧붙인 새 문구 |
    | 409 `NO_SUBSCRIPTION`, 또는 200 `{0, 0}`(방금 전부 삭제된 경우) | `no-subscription` | "알림을 받는 기기가 없어요. 알림을 껐다가 다시 켜 주세요." | "구독 없음" 그대로. `{0,0}`을 같은 안내로 묶는 것은 backend 권고 |
    | 429 | `retry` | "잠시 후 다시 시도해 주세요." | "잠시 후 다시 시도" 그대로 |
    | 200, `success_count`가 0이고 `failed_count ≥ 1` | `failed` | "알림을 보내지 못했어요. 잠시 후 다시 시도해 주세요." | 새 안내 — 뜻이 "잠시 후 다시 시도"와 같아 그 쪽으로 묶고 앞 문장만 더했다 |
    | 그 밖의 모든 경우(401, 정지·재동의가 아닌 403, 5xx, 응답 본문이 계약과 다름) 와 네트워크 오류(`fetch` 예외) | `failed` | 같은 문구 | 새 안내 — 같은 이유로 "잠시 후 다시 시도" 쪽으로 묶었다 |

    - 응답 본문이 없는 401은 로그인 만료일 수 있으나 이 화면의 다른 호출도 401을 특별히 다루지 않으므로(`save` 등) 같은 방식으로 `failed`로 묶는다. `(미확정)`
    - 200인데 `success_count`가 숫자가 아니면(계약 위반) `failed`로 본다. 숫자 검사는 `Number.isInteger`.
    - 429는 상태 코드만으로 분기한다(backend: 코드명은 바뀔 수 있음). 409는 `error === "NO_SUBSCRIPTION"`까지 본다(그 밖의 409가 생기면 `failed`).
  - 접근성: 버튼 글자가 이름이므로 `aria-label`을 따로 주지 않는다. 결과는 `role="status"`로 읽힌다. 비활성 대비는 기존 `Button`의 처리를 따른다.
  - 반응형: 버튼은 콘텐츠 열 안, 내용 폭(`self-start`)이다. 모바일 390px에서 결과 줄이 길면 줄바꿈한다.

#### 5. 내 정보 (청안 MemoryScreen → `/settings`, 신규)

- 파일: `app/(tabs)/settings/page.tsx`(신규, `requireSession({ requireProfile: true })`), `app/(tabs)/settings/memory/memory-client.tsx`(기억 구역, 현재 위치 유지 — `consent-privacy-wording.test.ts`가 이 경로를 읽는다), 신규 `app/(tabs)/settings/profile-section.tsx`(프로필 구역). `app/(tabs)/settings/memory/page.tsx`는 `/settings`로 리다이렉트만 한다(앱 안에 `/settings/memory` 링크는 없음, 47(b)).
- 구성(위 → 아래, 구역 사이 `gap-7`):
  1. `ScreenHeader` "내 정보".
  2. **AI가 기억하는 내 정보**(기억 구역): 소제목은 기존 이름 "AI가 기억하는 내 정보"를 쓴다(시안의 "AI가 기억하는 관심사"가 아니라 — 처리방침 고지가 이 이름을 가리키고 테스트가 고정함). 설명 줄: 기존 고정 문구("AI가 대화에서 알려주신 이름이나 호칭 같은 사실을 기억해 다음 대화에 활용해요. 기억한 내용은 여기서 확인하고 언제든 지울 수 있어요.") 그대로 + 시안 문장("추천과 알림은 이 문장들을 기준으로 골라요.")을 뒤에 붙인다. 목록은 `divide-y rule` + 테두리 + `bg-surface` + `rounded-control`, 각 행은 문장 `type-body` + 오른쪽 아이콘 버튼 "수정: 앞 12자…"(pencil)·"삭제: 앞 12자…"(trash)(각 44px, ink-3). 빈 목록은 기존 문구 "아직 대화에서 기억한 내용이 없어요."(상자 안).
     - 수정: 행이 편집 상태가 되어 텍스트 영역 + "취소"·"저장". 저장은 `PUT /api/preferences/:id`, 502 `EMBEDDING_FAILED`면 편집 상태를 유지하고 오류만 보인다(지금 동작 그대로).
     - 삭제: **5초 지연 삭제**. 삭제 버튼을 누르면 목록에서 바로 지우고 Toast "관심사를 지웠어요" + "되돌리기"를 5초 보인다. 서버 `DELETE /api/preferences/:id`는 5초가 지난 뒤 보낸다. 되돌리기를 누르면 요청을 보내지 않고 원래 자리에 되살린다. 그 사이 화면을 떠나거나(다른 탭으로 이동) 탭을 닫거나 숨기면 즉시 보낸다(`keepalive`) — 사용자가 지웠다고 생각한 개인정보가 남지 않게 하기 위함. 5초 안에 다른 항목을 지우면 앞 항목은 즉시 보내고 Toast는 뒤 항목 기준이다. 요청이 실패하면 항목을 되살리고 오류를 보인다. Toast 문구의 "관심사"는 시안 문구이며 기억 구역 이름("AI가 기억하는 내 정보")과 용어가 다르다 — 용어를 맞출지 확인([[glossary]]의 선호 정의).
  3. **프로필**: 소제목 "프로필", 읽기 전용 `dl`(라벨 96px + 값, `divide-y`): 출생연도 `YYYY년`, 성별, 직군, 재학·재직(표시명은 `_lib/profile-labels.ts`, 값 없음은 "-"). 아래 `type-meta` 줄: "AI에는 출생연도 대신 나이대(25~29세)를 보내요." 시안의 "이름과 이메일은 보내지 않아요" 부분은 쓰지 않는다 — 확인 항목 43에서 대화 속 이름·호칭을 기억하고 AI에 보내는 것을 허용했으므로 사실과 다르다. "수정" 버튼은 만들지 않는다(프로필 수정은 기존 설계에 없는 기능, API `PUT /api/profile`은 있음, 온보딩 폼에 기존 값 채우기가 따로 필요).
  4. **링크 목록**(위에 `rule` 선, 각 행 최소 높이 48, 아래 `rule` 선): "대화 기록" → `/conversations`(시안은 자리 표시 링크였음), "개인정보 처리방침" → `/privacy-policy`, "로그아웃"(`signOut` 후 `/login`, 정지 안내 화면의 로그아웃과 같은 호출), "탈퇴하기"(`text-danger`) → `/settings/account`.
- 데이터: `GET /api/preferences`, `GET /api/profile`. 두 호출 모두 기존 응답만 쓴다.
- 반응형: 열 폭 외 차이 없음. Toast는 콘텐츠 열 아래(`fixed`, 하단 탭 바 위 / 데스크톱은 바닥에서 24px).

#### 청안에서 가져오지 않는 것

본문 이미지 안내(`ImageNote`), 알림 "받는 기기", 답변 속 인용 번호, 프로필 수정 버튼, 휴대폰 틀·프로토타입 바로가기, 샘플 데이터 — 이유는 [[anyang-cheongan-design-adoption]] 8절. 이미지 배지(`ImageBadge`)는 2026-10-04(확인 항목 55)부터 가져온다(위 공지 목록 절). 공지 응답 필드(`is_pinned`·`image_count`·`attachments`)는 [[anyang-backend-api]]를 따른다.

## 테스트 방법

청안 디자인 적용(확인 항목 52) 화면의 테스트(빌드, vitest 추가분, 3폭 화면 확인 체크리스트)는 [[anyang-frontend-tasks]]의 "청안 디자인 적용" 절에 있다. 아래 항목 중 화면 구성·문구를 말하는 것은 "청안 디자인 적용 화면 스펙"이 우선한다.

- **로그인/가입**: Google 로그인 목(mock) 콜백으로 신규/기존 사용자 리다이렉트 분기 확인.
  이메일 중복 가입 시 409 오류 메시지 노출 확인. 잘못된 비밀번호 로그인 시 오류 메시지 확인.
  이미 이메일·비밀번호로 가입된 이메일로 Google 로그인 시도 시 `OAuthAccountNotLinked`
  오류를 비밀번호 오류와 다른 안내 문구로 표시하는지 확인.
- **개인정보 동의**: 체크박스 2개(수집·이용, AI 활용) 중 1개만 체크한 상태로 제출 시도 시
  진행되지 않는지 확인(제출 버튼 비활성 또는 오류). 둘 다 체크 후 이메일 가입은
  `POST /api/auth/register`에 `consents: { collection_use: true, overseas_transfer: true }`가
  담기는지, Google 신규 가입은 `POST /api/auth/consent`(같은 `consents` body) 호출 후
  `/onboarding`으로 이동하는지 확인. 처리방침 페이지 링크 이동 확인.
- **동의·처리방침 문구 단순화(확인 항목 41)**: `/consent`, `/privacy-policy` 화면의 렌더링된
  텍스트에 "DeepSeek", "Gemini", "중국", "국외", "미국" 문자열이 없는지 확인(코드 식별자
  `overseas_transfer`, API body 필드명은 문자열 검사 대상에서 제외 — 화면에 노출되는 텍스트만
  본다).
- **재동의 강제**: 인증 필요 API 응답을 403 + `{ error: "CONSENT_REQUIRED" }`로 목(mock)
  처리했을 때 공통 인증 가드가 `/consent`로 리다이렉트하는지, 두 체크박스를 다시 체크해
  제출하면 `POST /api/auth/consent`가 재호출되고 원래 흐름으로 복귀하는지, 이 화면에 탈퇴
  경로 링크가 함께 보이는지 확인.
- **비밀번호 찾기 링크 없음**: 로그인 화면에 비밀번호 재설정으로 이동하는 링크나 폼이
  존재하지 않고, "Google로 로그인" 안내 문구만 표시되는지 확인.
- **비밀번호 길이·시도 제한**: 비밀번호 8자 미만 입력 시 제출 전 인라인 오류가 뜨고 제출이
  막히는지 확인. 서버 400 `{ error: "PASSWORD_TOO_SHORT" }` 응답을 목으로 만들어도 같은
  오류가 표시되는지 확인. 로그인·가입 응답을 429 `{ error: "TOO_MANY_ATTEMPTS" }`로 목
  처리했을 때 차단 안내 메시지가 401 오류 메시지와 다르게 표시되는지 확인.
- **온보딩**: 필수 아님(null 허용) 항목을 비워도 제출 성공 확인. 제출 후 `/chat` 이동 확인.
- **채팅**: 스트리밍 응답이 토큰 단위로 화면에 이어붙는지 확인(목 SSE 스트림). 목 스트림에
  `event: citations` 블록을 DeepSeek 청크보다 먼저 넣었을 때 인용 카드가 말풍선 텍스트보다
  먼저 그려지는지, 카드에 `title`/`posted_at`만 표시되고 `source_url`은 카드에 노출되지
  않는지 확인. 카드 클릭 시 `/notices/[id]`로 이동하는지 확인. `data: []`(빈 배열) 목
  스트림에서는 인용 카드 행 자체가 그려지지 않는지 확인.
- **추천 공지 피드·상세**: 목록 카드 클릭 → 상세 진입 확인. `source_url` 링크가 새 탭으로
  열리는지 확인(원문 링크 무결성).
- **공지 목록 별표·칩·첨부·최신성(확인 항목 55)**: 세부 작업은 [[anyang-frontend-tasks]] 작업 단위 N1.
  - 단위(vitest, 환경은 `node`라 DOM이 없다. 새 의존성 없이 `react-dom/server`의 `renderToStaticMarkup`과 순수 함수로 검사하고, `next/link`가 이 환경에서 그려지지 않으면 조건 판정을 순수 함수로 빼서 검사한다. jsdom·testing-library 도입은 설계 변경이라 하지 않는다): ① `is_pinned` true일 때만 별표와 읽기 글자 "고정 공지", false/없음이면 둘 다 없음 ② `image_count > 0`일 때만 "이미지" 칩, 0/없음이면 없음 ③ 첨부 0개(`[]`·없음)면 첨부 영역이 없고, n개면 소제목 "첨부 파일 n개"와 파일명 n줄 ④ `source_url`이 http(s)가 아니면 원문 버튼과 첨부 안내가 없음 ⑤ `shouldRefetch`: 30초 이내 false, 이후 true, 조회 중 false ⑥ 병합: 새 1페이지가 앞에 오고 중복 `id`가 하나만 남음 ⑦ 재조회 구독 함수가 `visibilitychange`(visible)와 `pageshow`(persisted)에서만 콜백을 부르고 hidden·비복원 `pageshow`에서는 안 부르며, 해제하면 더 부르지 않음(가짜 `EventTarget` 사용).
  - 화면: 390px·1200px에서 `/notices`와 상세를 시안 설명(별표 고정 공지, "이미지" 배지, 날짜, 제목·발췌 각 2줄)과 대조한다. 시안 이미지 파일이 없어 이 대조는 계획서 설명 기준이다.
  - 탭 복귀: 목록을 연 채 다른 탭으로 갔다가 돌아오면 30초 뒤에는 요청이 1건 나가고 30초 안에는 안 나가는지, 갱신 중 화면이 깜빡이지 않는지 확인한다.
- **알림 설정**: 토글 on 시 브라우저 알림 권한 요청 프롬프트가 뜨는지 확인(로컬 개발
  `localhost`는 HTTPS 예외로 Notification API 사용 가능 — 운영 배포는 Vercel 기본 도메인
  (`*.vercel.app`)도 HTTPS이므로 커스텀 도메인 연결 전에도 문제 없다 — 커스텀 도메인은
  나중에 붙는다([[anyang-deployment-portability]] 원칙 5). 권한 거부 시 토글이 다시 꺼지는지
  확인. 허용 시 `POST /api/push/subscribe` 호출 페이로드에 `endpoint`/`p256dh`/`auth`가
  담기는지 확인. 토글 근처에 "알림을 켠 시점 이후 공지만 알림 대상"이라는 안내 문구가
  표시되는지 확인.
- **테스트 알림 보내기(확인 항목 58)**: 세부 작업은 [[anyang-frontend-tasks]] 작업 단위 T1~T3.
  - 단위(vitest, 환경 `node`, 새 의존성 없음): `describeTestResult` — ① 200 `{1,0}` → `success`, 문구에 "1대" ② 200 `{2,1}` → `success`, "2대"와 "1대는 보내지 못했어요" ③ 409 `NO_SUBSCRIPTION` → `no-subscription` ④ 409 다른 코드·본문 없음 → `failed` ⑤ 200 `{0,0}` → `no-subscription` ⑥ 200 `{0,2}` → `failed` ⑦ 429(본문 있음·없음 모두) → `retry` ⑧ 401·500, 403(본문 `ACCOUNT_SUSPENDED` 포함) → `failed` ⑨ 200인데 body가 `null`·`success_count`가 문자열이면 `failed` ⑩ 네트워크 오류를 `status 0, body null`로 넘기는 경우 `failed`(화면 쪽에서 `fetch` 예외를 이 값으로 바꿔 넘긴다). 서비스워커 `parsePushPayload`(기존 `web/test/frontend-push.test.ts`에 추가) — ⑪ `{title:"테스트 알림입니다", url:"/settings/notifications"}` → url 그대로, title 그대로 ⑫ `url:"//evil.com"`·`"https://evil.com"`·`"/\\evil.com"`·`"settings"`·숫자·빈 문자열이면 무시하고 기존 규칙(`notice_id` 있으면 상세, 없으면 `/notices`) ⑬ 기존 두 테스트(`notice_id`만, 빈 payload)가 그대로 통과 ⑭ `url`과 `notice_id`가 함께 오면 `url`.
  - 화면(실제 실행): `npm run dev`로 `/settings/notifications`를 연다. 알림이 켜진 상태(구독 가능한 로컬 환경, 안 되면 `GET /api/notify-settings`를 목으로 만들어 `enabled`로 보이게)에서 `POST /api/notify-settings/test` 응답을 목(DevTools 요청 가로채기 또는 임시 라우트)으로 200 `{1,0}`·409·429·500·네트워크 끊김을 차례로 만들어, 버튼이 요청 중 비활성·"보내는 중..."이 되고 끝나면 풀리는지, 결과 줄이 표의 문구로 나오는지, 다시 누르면 이전 줄이 지워지는지, 알림이 꺼진 상태·iOS 브라우저 탭 상태(홈 화면 추가 안내가 나오는 경우)에서는 버튼이 없는지, 390px·1200px에서 줄바꿈·가로 스크롤이 없는지 확인한다. 실제 기기 수신과 클릭 이동은 구독이 있는 실제 기기가 필요해 구현 에이전트가 못 하면 못 했다고 보고하고 사용자·메인 세션이 확인한다.
- **서비스워커**: 브라우저 개발자 도구 Application 탭에서 서비스워커가 `activated` 상태인지
  확인. 목 푸시 이벤트를 개발자 도구에서 수동 트리거해 알림이 표시되는지 확인. 테스트 알림 payload
  `{"title":"테스트 알림입니다","url":"/settings/notifications"}`를 같은 방법으로 보내 알림을
  누르면 `/settings/notifications`로 이동하는지 확인(확인 항목 58).
- **PWA 설치**: 모바일 브라우저(Chrome/Safari) 또는 데스크톱 Chrome에서 "홈 화면에 추가"/설치
  프롬프트가 뜨는지 확인. manifest 유효성은 Chrome DevTools "Application → Manifest" 패널로
  오류 없는지 확인.
- **"AI가 기억하는 내 정보"**: 목록 표시, 수정 후 목록에 반영되는지(재임베딩 실패 시 값이
  되돌아가는지) 확인, 삭제 후 목록에서 사라지는지 확인. 빈 목록 안내 문구 확인. **(확인 항목
  43, 신규)**: 이름 기억 안내 문구가 목록 위(또는 빈 목록 문구 위)에 항상 표시되는지 확인.
- **처리방침 이름 기억 고지(확인 항목 43, 신규)**: `/privacy-policy`의 "AI 처리" 절에 이름·
  호칭 기억 고지 문장이 렌더링되는지 확인. 기존 확인 항목 41 금지 문자열 테스트
  (`web/test/consent-privacy-wording.test.ts`)가 새 문장에서도 통과하는지(추가 문자열
  검사 없이 기존 테스트를 재실행) 확인.
- **대화 히스토리**: 목록이 `updated_at desc` 순으로 오는지 확인. 항목 클릭 시 과거 메시지가
  로드되며 `/chat`에서 이어지는지 확인. 새 대화 시작 버튼이 빈 대화로 진입하는지 확인.
- **계정 탈퇴 확인**: 탈퇴 버튼 클릭 시 확인 다이얼로그가 뜨는지, 취소 시 `DELETE /api/account`
  가 호출되지 않는지, 확인 시 호출되고 성공 후 세션이 종료돼 `/login`으로 이동하는지 확인.
  보관 안내 문구가 표시되는지 확인.
- **도메인 변경 재구독 유도**: 구독이 없는데 `enabled=true`인 상태를 목으로 만들어 배너가
  뜨는지, 재구독 흐름이 다시 동작하는지 확인.
- **인증 가드**: 미로그인 상태로 `/chat`, `/notices`, `/settings/notifications` 직접 접근 시
  `/login`으로 리다이렉트되는지 확인. 프로필 없는 로그인 사용자가 `/chat` 접근 시
  `/onboarding`으로 리다이렉트되는지 확인. 동의하지 않은 사용자가 `/chat` 등에 접근 시
  403 + `{ error: "CONSENT_REQUIRED" }` 응답을 기준으로 `/consent`로 리다이렉트되는지
  확인(제안 — 판정 방식).
- **정지 계정 안내**: 정지된 계정(이메일·비밀번호, Google 모두)으로 로그인이 정상적으로
  성공하는지(차단되지 않음) 확인하고, `session.suspended`가 true인 상태를 목으로 만들어
  로그인 직후 정지 안내 화면으로 이동하는지 확인. 정지 안내 화면에서 로그아웃·탈퇴 외 다른
  화면 이동을 시도하면 403 + `{ error: "ACCOUNT_SUSPENDED" }` 응답을 기준으로 정지 안내
  화면으로 되돌아가는지(세션이 종료되지 않는지) 확인. 이 화면에 탈퇴 경로 링크가 함께
  보이는지 확인.
- **관리자 접근 차단**: 관리자가 아닌 로그인 사용자(또는 `ADMIN_EMAILS`에 있지만 이번
  세션을 Credentials로 로그인한 경우)로 `/admin/*` 4개 화면에 직접 URL 접근 시 데이터가
  렌더링되지 않고 403 + `{ error: "ADMIN_ONLY" }` 응답 기준으로 "관리자 계정이 아닙니다"
  안내와 함께 `/chat`으로 리다이렉트되는지 확인. 소스맵·번들(`grep`으로 빌드 산출물 검사)에
  `ADMIN_EMAILS` 값이나 관리자 이메일 문자열이 포함되지 않는지 확인.
- **관리자 이메일 가입 차단**: `ADMIN_EMAILS`에 있는 이메일로 이메일·비밀번호 가입 시도 시
  403 + `{ error: "ADMIN_EMAIL_RESERVED" }` 응답을 기준으로 인라인 오류 문구가 표시되고
  가입이 진행되지 않는지 확인.
- **관리자 원문 비노출**: 4개 관리자 화면 어디에도 `messages`/`preference_text` 등 대화·기억
  원문을 렌더링하는 코드 경로가 없는지 확인(해당 API 응답에 그 필드가 없으므로 코드 리뷰로
  확인 — 자동 테스트로는 응답 payload에 없는 필드를 화면이 참조하지 않는지 타입 체크로
  간접 확인).
- **공지 수집 관리 — 보드 수집 이력 표시(확인 항목 56, 신규)**: 세부 작업은 [[anyang-frontend-tasks]] 작업 단위 K1.
  - 단위(vitest, 환경 `node`, 새 의존성 없음): `describeRun` 순수 함수 — ① `trigger_type` manual/scheduled/그 밖 → "수동"/"자동"/원문 ② `status` success/failed/running/그 밖 ③ `collected_count` 숫자 → "새 글·바뀐 글 N건", 0도 "0건", null → "-" ④ `error_summary` 코드 5종 각각 → 문구 + 원문 보존, `ip_blocked kind=full` 처럼 뒤에 글이 붙어도 첫 단어로 매핑되고 원문 전체가 남음 ⑤ `rejected=2, error=1` → 숫자 2·1이 들어간 문구, `rejected=x` 같은 변형 → 원문 ⑥ `null` → 문구 없음 ⑦ 표에 없는 값(예: `ingest_auth`, 임의 글)은 원문 그대로 ⑧ 키 이름이 코드로 시작하지만 다른 단어(`ip_blocked_x`)는 매핑하지 않음(첫 단어 완전 일치). 410 판정 순수 함수 `isDirectCollectDisabled(status, body)` — 410+`{error:"DIRECT_COLLECT_DISABLED"}`만 true, 410+다른 본문·본문 없음·500은 false.
  - 화면(실제 실행): 관리자 계정으로 `/admin/collect-runs`를 연다. 로컬에서 열 수 없으면(DB·관리자 로그인 설정 필요) 못 했다고 보고하고, 목 응답(`POST` 410, `GET`에 실패·성공·알 수 없는 값 행)으로 `npm run dev` 화면을 확인한다. 확인 항목: 버튼 클릭 → 410 목 → 안내(오류 색 아님)가 뜨고 버튼이 비활성, 새로고침하면 다시 눌러 볼 수 있음 / 500 목 → 기존 오류 문구 / 200 목 → 목록 갱신 / 이력 행의 상태 글자·문구 / 390px·1200px에서 줄바꿈·가로 스크롤 없음 / 안내 `role="status"`가 스크린리더에 읽힘.
  - 회귀: 공지 목록 탭·숨김/해제 동작 불변(기존 11절 테스트 그대로).
- **사용자 화면 불변 확인(확인 항목 56)**: `/notices`, `/notices/[id]`, 채팅 인용의 파일·API 호출이 이번 작업에서 바뀌지 않았는지 diff로 확인한다(`git diff --stat`에 `app/(tabs)/**`가 없어야 함). `npm test`의 기존 공지 관련 테스트가 그대로 통과해야 한다.

  완료 후 목록이 갱신되는지 확인(스위치가 켜진 환경 기준, 꺼진 환경은 위 56 항목). "공지 목록" 탭의 필터·페이지 이동·숨김/해제 확인 절차·

- **알림 발송 현황·외부 API 사용량**: 날짜 범위 변경 시 표 데이터가 갱신되는지 확인.

- **채팅 뒤로가기 유지(확인 항목 60, 3-1절)**: 단위 테스트는 `web/test/frontend-chat-snapshot.test.ts`(가짜 저장소 주입, 브라우저 없음)로 다음을 확인한다. ① 키가 `anyang:chat:v1:{userId}:{conversationId}` 형식이고 사용자·대화가 다르면 키가 다르다. ② 보관 → 읽기 왕복에서 인용 포함 messages·`scrollTop`·`atBottom`·`streaming`이 그대로다. ③ 깨진 JSON, `v` 불일치, `messages`가 배열이 아님, 원소 모양 불일치는 읽기에서 `null`이고 해당 키가 지워진다. ④ 글자 수 상한 초과 시 오래된 쌍부터 버리고 최근 것이 남으며 맨 앞이 assistant만 남지 않는다. ⑤ 대화 10개 초과 시 `savedAt`이 가장 오래된 키부터 지워진다. ⑥ `setItem`이 던지면 가장 오래된 키를 지우고 한 번만 다시 시도하며 그래도 실패하면 예외 없이 끝난다. `getItem`·`setItem`·`removeItem`이 모두 던져도(접근 불가) 예외가 새지 않는다. ⑦ `clearAllChatSnapshots`가 접두사가 같은 키만 모두 지우고 다른 키(예: 다른 앱 키)는 남긴다. ⑧ 서버 병합(`mergeStreamingSnapshot`): 서버 메시지 수가 보관분 이상이면 서버 목록에 보관분 `citations`가 같은 위치 assistant에 옮겨지고, 적으면 보관분이 그대로이며 "중간 멈춤" 표시가 켜진다. 수동 시나리오(실행 환경에서 사람이 한다, 확인하지 못했으면 못 했다고 보고): (가) 인용 5건이 달린 답변에서 카드 1 열기 → 뒤로 → 대화·인용 카드·스크롤 그대로 → 카드 2 … 5까지 순서대로 반복(상세의 "‹ 공지" 버튼으로 한 번, 브라우저 뒤로가기로 한 번 모두). (나) 같은 화면에서 새로고침 → 대화·인용·스크롤이 서버 조회 없이 복원(개발자 도구 네트워크에 `/messages` 요청 없음). (다) 첫 질문 직후 URL이 `/chat?conversation_id=…`로 바뀌고 히스토리 길이가 늘지 않으며, 답변이 스트리밍되는 동안 끊기거나 화면이 비지 않는다(3-1절 7번의 핵심 확인). (라) 답변 스트리밍 중 인용 카드를 눌러 이동했다가 뒤로 → 3-1절 6번대로 표시. (마) 새 대화 버튼 → 빈 화면, 뒤로가기 → 이전 대화(인용 포함) 복귀. (바) 개발자 도구에서 해당 sessionStorage 키를 지운 뒤 새로고침 → 본문은 서버에서 복원되고 인용 카드만 없다. (사) 로그아웃 → 같은 탭에서 다른 계정으로 로그인 → 이전 사용자의 대화가 보이지 않고 sessionStorage에 `anyang:chat:v1:` 키가 없다. (아) 재로그인 후 대화 기록에서 옛 대화를 열면 본문은 있고 인용은 없다. (자) sessionStorage를 막은 모드(또는 `setItem` 강제 오류)에서도 채팅이 동작하고 새로고침 뒤 본문이 서버에서 복원된다. `npm test`·`npm run build` 통과가 커밋 조건이다.
